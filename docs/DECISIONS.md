# PO 결정 로그

PO가 내린 결정을 번호·날짜와 함께 기록한다. **결정은 여기에만 쌓고, HARNESS에는
요약표만 둔다.** 나중 결정이 이전 결정을 대체하면 지우지 말고 "→ #N으로 대체됨"을
남긴다 — 채록에서 "08-08 지시가 08-05 지시를 대체한다"처럼 이력이 남아야
왜 바뀌었는지 다음 세션이 안다.

형식:

```
## #1 (YYYY-MM-DD) 결정 제목
- 결정: 무엇을 하기로 했나 (한 문장)
- 이유: 왜 (대안과 비교했으면 그것도)
- 영향: 어느 코드/문서/절차가 바뀌나
- 상태: 반영 완료 / 진행 중 / 대기
```

---

## #1 (2026-08-14) 조직 개편 — BD·PM·BRAND 신설, PD 범위 축소

- **결정**: 역할을 6개에서 9개로 늘린다. **BD**(시장·사업성·BM), **PM**(PRD·범위·
  일정·품질), **BRAND**(브랜드 아이덴티티·컨셉 디자인)를 신설하고, **PD**는
  "앱·서비스·프로모션 디자인 + UX Writing"으로 좁힌다.
- **이유**: PO 지시. 기존 PD 한 명이 PRD·UX·디자인 시스템·라이팅을 다 지고 있었고,
  사업성 검토는 담당이 아예 없어 오케스트레이터가 임시로 떠맡고 있었다(렉시오
  `BUSINESS_CASE.md`가 그 사례).
- **파생 결정 (오케스트레이터가 경계를 정하고 문서화, PO 확인 필요)**:
  1. **PRD 소유권을 PD → PM으로 옮긴다.** 단, PRD는 **한 파일**로 유지하고
     PM(문제·범위·성공 기준) → PD(화면·상태·카피) **순차**로 쓴다. 두 문서로
     쪼개면 기능의 기준이 갈라져 서로 어긋난다.
  2. **PM에게 위임 권한을 주지 않는다.** 위임은 오케스트레이터만 한다 —
     관리자가 둘이면 같은 일이 두 번 돌거나 아무도 하지 않는다.
     PM은 제품의 시간축(마일스톤), ORCH는 세션의 시간축을 본다.
  3. **BRAND가 원본, PD가 파생.** 컬러·타이포·톤은 `BRAND.md`에서만 정하고 PD의
     디자인 시스템은 그것을 파생시킨다.
- **영향**: `TEAM.md`(조직도·RACI·기능 사이클·위임 규칙·에스컬레이션·기록 체계),
  `.claude/agents/{bd,pm,brand}.md` 신설, `.claude/agents/pd.md` 개정,
  `.claude/commands/kickoff.md`, `README.md`, `docs/HARNESS.md`.
  신설 문서 2종 등록: `docs/ROADMAP.md`(PM), `<제품>/docs/BRAND.md`(BRAND).
- **상태**: **PO 승인 완료 (2026-08-14) — 확정.** 파생 결정 3건(PRD 소유권 ·
  PM 위임권한 없음 · BRAND 우선)이 승인됐다. 이제 조직 경계는 확정 사실이며,
  바꾸려면 새 결정 번호로 대체한다 (이 항목을 고쳐 덮지 않는다).

## #2 (2026-08-14) 역할 하네스 개편 — Role Definition 도입 + 협업 관행 반영

- **결정**: PO 지시로 9개 역할 하네스를 개편한다. ① 각 하네스 맨 앞에
  **Role Definition 8줄**(한 줄 정의·핵심 질문·성공의 정의·주 산출물(DRI)·
  입력→출력·하지 않는 일·권한 경계·참조 모델)을 붙인다. ② 협업으로 이름난
  팀들의 관행 중 **공통 요소만** 골라 각 역할에 적용한다. ③ PO의 철학을
  `TEAM.md` §0으로 성문화한다. ④ 팀 소개(조직도·주요 특성)를 `README.md`에 싣는다.
- **이유**: PO 지시. 기존 하네스는 "책임·규칙·DoD"는 있었지만 **역할의 경계와
  성공 기준이 한눈에 안 보였다.** 위임 프롬프트를 쓸 때마다 경계를 매번 다시
  설명해야 했고, 그게 세션마다 반복되는 비용이었다.
- **파생 결정 (오케스트레이터가 정하고 문서화, PO 확인 필요)**:
  1. **주 산출물 = DRI 선언.** 각 역할은 파일 하나의 주인이다 (Apple DRI /
     Amazon single-threaded owner). 소유자가 둘인 파일은 만들지 않는다.
  2. **표준 보고 형식 5줄**을 전 역할 공통으로 강제한다 (`TEAM.md` §3).
     5번 "리스크 한 줄"은 형식이 아니라 자기검증 장치다.
  3. **위임 패키지 5종**을 오케스트레이터의 의무로 못 박는다 (`TEAM.md` §3).
  4. **구조는 베끼지 않는다.** 스쿼드·트라이브 같은 조직 구조, 회의체(베팅
     테이블 등), 분기 OKR, SLO 수치 운영은 1인 PO 팀에 과해서 채택하지 않고
     개념만 가져왔다. 채택/미채택 목록과 출처는 `TEAM.md` §7에 남겼다.
- **영향**: `.claude/agents/*.md` 9종 전부, `TEAM.md`(§0 철학 · §3 위임 패키지·
  표준 보고 형식 · §7 관행의 뿌리), `README.md` 전면 개편, `AGENTS.md`.
- **상태**: **PO 승인 완료 (2026-08-14) — 확정.** 파생 결정 4건 전부 승인됐다
  ("지금 방식 좋아"). 다음 세션부터 **위임 패키지 5종**과 **표준 보고 형식 5줄**은
  권고가 아니라 **기본값**이다. 지키지 않은 위임은 오케스트레이터의 실수로 센다.


## #3 (2026-09-02) 하루담(가제) 서비스 기획 — BD→PM/BRAND→PD/TL→QA 1회전

- **결정(초안, PO 판정 대기)**: PO의 새 아이템 "하루담"(자녀가 선물하고 부모가 매일
  AI 인터뷰에 답해 자서전이 되는 서비스)을 0→1 기능 사이클로 기획했다. BD 판정은
  **Go-if**(조건 G1~G5, 중단 K1~K7). 착수·가격·채널·제품명 **확정은 PO 몫이라 대기**.
- **이유**: PO 요청(시장성·고객군·지불의사·PRD·브랜딩·디자인·기술구조를 목표 9/10로).
- **오케스트레이터가 이 세션에서 정한 것(PO 확인 필요)**:
  1. **작업 순서** BD → (PM ∥ BRAND) → (PD ∥ TL) → QA. 기술 스파이크(TECH_SPIKE)를
     BD와 병렬로 먼저 태워 PM의 범위 절단 입력값으로 썼다.
  2. **부모 답변 채널 충돌**(BD 앱=V2 ↔ TL 앱 우선 B′)을 PM이 PRD §10-A **PO 결정
     1순위 + `〔가정: 채널〕` 태그**로 봉합. V0 마이크 실측이 결정권을 쥔다.
  3. QA 판정 **조건부 통과**의 정합 결함 5건(F1 북극성 분모 높음 외)을 **ORCH가 각
     역할 모자로 직접 문서 수정**해 닫음(작은 손질은 ORCH 직접, pm.md 허용).
- **영향**: `apps/harudam/docs/`(신규 8파일), `docs/ROADMAP.md`(신규 — 하루담 절 추가),
  `docs/HARNESS.md`(지금 상태·확정된 결정·더 볼 것).
- **상태**: **PO 판정 대기.** 착수 Go/보류·채널·가격·제품명·대외 접촉 승인 전까지
  구현 착수 금지. 다음 세션은 HARNESS "다음 세션이 챙길 것 (하루담)"부터 본다.

- **추가 (2026-09-03) — GROWTH 감성 마케팅 전략 + 감정 레버 정정.** PO가 감정 레버를
  정정했다(대화): "죄책감/뒤늦은 후회"가 아니라 **자녀가 도구로 부모에게 따뜻하게 묻고
  감동받고, 부모는 소통에 마음을 쏟을 장치** — 즉 **오늘의 양방향 감동·연결**이 척추다.
  GROWTH가 `apps/harudam/docs/GTM_STRATEGY.md`에 반영(후회는 랜딩 헤드라인 한 곳의 약한
  부차 각으로만, BRAND A1②). **설득→개발 트리거**를 가짜 문 랜딩 전환율=BD G1/K1로 성립
  시킴. BRAND 개정 제안 1건(A1② 각주, 긴급도 낮음)은 BRAND/PO 판단 대기. 상태: **PO 검토
  대기**, 랜딩 발행 미승인.

# 플레이북 — 디버깅 원칙

채록의 실사고들(제목 3연속 헛수정, 키보드 6차전, 결제 사고 시리즈, 파이프 사고)
에서 뽑은, 역할 무관 공통 원칙이다. 각 원칙 뒤에 그것을 만든 사고가 붙어 있다.

## 1. 추측 금지 — 원인은 재서 확정한다

재현 → 최소 실험 → 로그로 좁힌 뒤에만 "원인"이라 부른다. 채록은 제목 버그로 세 번,
결제로 한 번 헛짚었고, 수정 기록에 "**진단이 틀렸다**"가 남아 있다. 헛수정의 비용은
수정 자체가 아니라 **틀린 전제가 다음 진단을 오염시키는 것**이다.

## 2. 오류를 코드와 함께 노출한다

"동기화하지 못했어요"는 진단 불가, "sync.failed (unavailable)"는 스크린샷 한 장으로
판별 가능. unavailable=연결, permission-denied=권한/등급 — **코드 하나가 진단을
한 방에 끝낸다.** 새 실패 경로를 만들 때 코드 노출은 선택이 아니라 기본값이다.

## 3. 코드 밖을 목록에 넣는다

채록의 굵직한 "버그" 여럿이 코드 밖에 있었다:
- 콘솔 설정 (익명 로그인 꺼짐 → ADMIN_ONLY_OPERATION)
- 계정 데이터 (서버 등급 미부여 → permission-denied)
- 스토어 전파 지연 (상품 메타데이터 하룻밤)
- 외부 사이트 변경 (og 메타 변경으로 파싱 품질 저하 — 배포 없이 깨짐)

"코드가 아닐 가능성"을 조사 목록의 1급 항목으로 둔다.

## 4. 검증은 종료코드로 판정한다

`verify | tail`을 && 체인에 넣으면 파이프가 실패 종료코드를 삼킨다 — 채록에서
깨진 번들이 라이브로 나간 사고의 직접 원인. `set -o pipefail` 또는
`> log 2>&1; [ $? -eq 0 ]` 꼴만 쓴다.

## 5. 레이아웃 계측은 움직이지 않는 것에만 건다

키보드 상승 중 **움직이는 래퍼를 잰** 값이 스냅으로 확정돼 입력창 낙하 회귀를
만들었다. 계측을 걸기 전에 묻는다: **"이 값이 애니메이션 중에도 참인가?"**
프레임이 고정된 컨테이너를 재라.

## 6. 수정이 회귀를 만든다

키보드 5차 수정이 6차 회귀를 만들었다. 수정 직후에는 수정이 건드린 경로의
**인접 시나리오**를 돌린다. 사고였던 경로는 회귀 시나리오/검증 규칙표에 박제한다 —
같은 사고는 두 번 나지 않아야 한다.

## 7. 기기가 사실이다

사용자가 "되는데?"라고 하면 기기에서 본 게 사실이다 — 내 추론이 틀린 쪽을 먼저
의심한다. 역도 같다: 내 시뮬레이터가 "된다"는 실기기의 "안 된다"를 이기지 못한다.
판별 신호(번들 태그=커밋 7자, 오류 코드)를 미리 심어두면 이 대화가 짧아진다.

## 8. 재현 조건을 조합으로 좁힌다

익스텐션 414 버그는 "로그아웃 상태 + 긴 본문" 조합에서만 났고, 첫 실행 낡은 등급은
"테스트 이력 많은 계정 + 내장 번들 1회차"에서만 났다. 단일 변수로 재현이 안 되면
**상태의 조합**을 의심한다.

## 9. 외부 의존에는 프로브를 둔다

타사 사이트·API의 모양에 기대는 코드는 우리 배포와 무관하게 깨진다. 실제 대상에
대고 도는 주기 프로브를 두되, **모양이 아니라 불변식**을 검사하고 모양은 스냅샷
대조로 드리프트 조기 경보에만 쓴다. 접속 실패(데이터센터 IP 차단)는 경고,
빨강은 위반·드리프트에만 — 늑대소년이 된 프로브는 없는 것보다 나쁘다.

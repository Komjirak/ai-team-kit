# 플레이북 — OTA와 네이티브 빌드 운용

Expo(EAS) 기준으로 쓰였지만 원칙은 어느 OTA 체계에도 적용된다.
핵심 질문은 하나다: **"이거 OTA로 안 되나?"가 항상 먼저.**

## 빌드 예산

- 무료 플랜의 월 빌드 한도는 심사 대응의 생명줄이다. **빌드는 심사·네이티브
  변경에만** 쓴다. JS 수정은 전부 OTA로.
- 시뮬레이터·preview 프로필 빌드도 카운트를 먹는다 — 무빌드 검증 경로(export 등)를 먼저 쓴다.
- 빌드를 걸기 전에 반드시 묻는다: OTA로 되는가? 남은 횟수는? 이 빌드의 용도는?

## OTA로 못 바꾸는 것 (재빌드 목록)

- 네이티브 모듈 추가·변경
- 권한 문구 (Info.plist)
- app 설정의 네이티브 값 (scheme, 아이콘, 스플래시 등)
- 앱 버전, `runtimeVersion` 정책
- `updates.fallbackToCacheTimeout` — 네이티브에 박힌다. 빌드 걸기 전에 값을 정한다
  (0 = 첫 실행은 내장 번들·즉시 시작, 3~5초 = 첫 실행에 최신 OTA·느린 망에서 스플래시 볼모)

## runtime·버전 규칙

- **runtimeVersion은 최상위 `{policy:"appVersion"}` 하나만.** 플랫폼별 오버라이드를
  두면 최상위를 이겨서 OTA가 어느 빌드에도 안 닿거나 플랫폼별로 갈린다.
- **네이티브 모듈을 추가·변경하면 앱 버전을 올린다** — 안 올리면 옛 빌드가 새 모듈을
  require하는 JS를 받아 시작조차 못 한다.
- 발행 전 **옛 바이너리와 dependencies 동일성**을 확인한다 (새 네이티브 모듈 없음 = 안전).

## 발행 규율

- **실사용자가 붙은 runtime의 OTA**: verify + 양 플랫폼 export + 실기기 확인 후,
  가급적 오전(대응 가능 시간대)에 발행. "던지고 실기기로 잡는" 사이클은 테스터
  전용 시절의 것이다.
- **플랫폼 플래그를 항상 명시** — 같은 runtime에 다른 플랫폼 테스터가 붙어 있을 수 있다.
- 발행 계보를 HARNESS에 남긴다: `그룹/업데이트 ID | 커밋 | 내용` 표. 사고가 나면
  이 표가 롤백과 진단의 지도다.

## "적용됐나?"를 판별하는 법

- **번들에 커밋 해시(7자)를 스탬프한다** (빌드 시점에 extra 필드로 주입) — 앱 설정
  화면 맨 아래에 노출. `git log`와 바로 대조된다. 빌드든 OTA든 읽는 법이 같다.
- 업데이트 ID는 커밋과 맞춰볼 길이 없어 답을 주지 못한다 — 채록에서 이미 실패한 방식.
- OTA는 두 번째 실행에 적용된다 (fallbackToCacheTimeout 0 기준) — 1회차에서 낡은
  화면을 보고 "적용 안 됐다"고 오판하지 않는다.

## 검증 게이트 (발행 전)

```
npm run verify > /tmp/v.log 2>&1; [ $? -eq 0 ] && echo OK   # 종료코드로 판정
npx expo export --platform ios
npx expo export --platform android   # 타입은 통과해도 런타임 import가 깨지는 걸 잡는다
```

파이프로 출력을 자르면 종료코드가 삼켜진다 — 채록에서 깨진 번들이 라이브로 나간
사고의 원인이 정확히 이거였다.

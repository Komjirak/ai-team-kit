## A. 시니어 한국어 STT 실현성 (G4)

### A-1. 이 제품의 STT 요구 조건 — 판정 기준을 먼저 정한다

일반 STT 도입과 다른 조건 3개가 판정을 좌우한다:

1. **실시간이 아니다.** 하루 한 답변의 **사후 정리**다. 지연 허용치가 분 단위 이상
   → 배치(비동기) 처리 가능 → 가장 싼 요금 구간과 가장 정확한(느린) 모델을 쓸 수 있다.
2. **원음이 어차피 서버에 남는다.** R7에 따라 책의 QR 원음 재생까지가 V1 범위이므로
   녹음 파일 업로드는 필수다 → 온디바이스 STT의 "서버 비용 절감" 이점이 절반으로 준다.
3. **출력물은 자막이 아니라 '읽을 만한 문단'이다.** 오인식 몇 %보다 "간투사·반복·사투리
   억양이 섞인 구어를 문어로 정리"하는 후처리 품질이 체감을 결정한다.

**고령자·사투리 전용 데이터셋은 포함돼 있지 않다.**

### A-3. 고령자 발화·사투리 — 아는 것과 모르는 것

**아는 것 (출처 있음):**

- 고령자 발화는 사투리·억양 등 발화 특성이 다른 연령대와 뚜렷이 달라, 정부(NIA)가
  **고령자 전용 음성 데이터셋을 별도 구축**했다 — [AI Hub 자유대화 음성(노인남여)](https://www.aihub.or.kr/aihubdata/data/view.do?dataSetSn=107)
  (60세 이상 자유대화 + 전사 + 녹음환경 메타데이터). "고령자 대상 서비스는 해당 연령대
  음성 인식 데이터 구축이 성공 전제"라는 것이 이 데이터셋의 구축 취지다.
  → **범용 모델의 고령자 성능 저하는 업계가 인정한 사실**이라는 정황 근거.
- 고령자 ASR은 별도 연구 분야로 존재한다 — [고령자 ASR용 데이터 증강 연구 (arXiv)](https://arxiv.org/pdf/2604.24770) ·
  [고령자 화자 적응 연구 (arXiv)](https://arxiv.org/pdf/2606.16539) (프록시 차단으로 원문 미열람, 초록 검색 기준).
- 한국어에서 사투리·간투사가 섞인 실제 대화는 짧고 명확한 문장 대비 인식 격차가
  크다 — [한국어 사투리 음성 인식 연구 (KoreaScience)](https://www.koreascience.kr/article/CFKO202221536069009.page?lang=ko).
- 파인튜닝·후처리로 격차가 크게 줄어든 사례: Whisper + KcBERT 후처리로 CER
  5.12%→1.88%(clean), 22.65%→10.17%(noise) — 한국정보과학회 계열 연구
  (검색 요약 기준, [관련 KISTI 논문](https://scienceon.kisti.re.kr/srch/selectPORSrchArticle.do?cn=JAKO202330043250854)).

**모르는 것 (`미확인` — 이 스파이크로 닫을 수 없음):**

- 위 상용 API들의 **고령자·사투리 데이터셋에서의 CER** — 공개 벤치마크 없음.
  국내 특화 엔진(리턴제로·클로바)이 AI Hub 노인 데이터를 학습에 썼는지도 비공개.
- 따라서 **G4는 데스크 리서치로 Go를 닫을 수 없고 실측이 필요하다**:
  AI Hub 노인남여 데이터 샘플 30~50문장(사투리 화자 포함)으로 후보 2~3개
  (RTZR·클로바·gpt-4o-transcribe)를 CER 비교 — **1~2일 작업 `추정`**.
  AI Hub 데이터는 승인 절차만 있으면 무료다.

### A-4. 내장 받아쓰기(무료)로 MVP가 되는가 — **안 된다 (보조로만)**

| 항목 | iOS | Android |
|---|---|---|
| API | SFSpeechRecognizer (ko-KR 지원) | SpeechRecognizer ([공식](https://developer.android.com/reference/android/speech/SpeechRecognizer)) |
| 한계 | **세션당 1분 하드 리밋**, 버퍼 기반은 조용히 실패·부분 결과 가능 ([Picovoice 가이드](https://picovoice.ai/blog/ios-speech-recognition/)). 무제한 SpeechAnalyzer는 **iOS 26 전용** ([해설](https://antongubarenko.substack.com/p/ios-26-speechanalyzer-guide)) | 짧은 발화 지향, 침묵 시 자동 종료. 온디바이스 품질은 기기·제조사 편차 `추정`. GenAI 고품질 모드는 Pixel 10 한정 ([ML Kit](https://developers.google.com/ml-kit/genai/speech-recognition/android)) |

세 가지 이유로 탈락:

1. **노인 답변은 1~3분 이상 이어지고 중간에 멈칫한다** — 1분 세션 제한·침묵 자동 종료와
   정면 충돌. 끊김은 곧 이탈(R2)이다.
2. 실시간 받아쓰기 UX는 오인식이 **화면에 그대로 보여** 시니어를 위축시킨다.
   "녹음만 하세요, 정리는 밤사이 됩니다"가 이 제품의 올바른 UX다 `추정`.
3. 원음은 어차피 서버로 올린다(R7 QR 재생) — 온디바이스 STT를 써도 업로드는 사라지지 않는다.

→ MVP는 **"로컬은 녹음만, 변환은 서버에서"**. 내장 받아쓰기는 후순위(짧은 텍스트 수정 등)로.

### A-5. "STT → LLM 후처리" 파이프라인 — 실용적이다

- LLM 후처리로 ASR 오류를 유의미하게 교정할 수 있다는 근거가 축적돼 있다 —
  [GenSEC 챌린지·베이스라인](https://arxiv.org/html/2409.09785v3) ·
  [억양 화자 전사에 LLM 교정 적용 (medRxiv)](https://www.medrxiv.org/content/10.1101/2025.08.29.25333548.full.pdf).
  한계도 명확하다: **원문에 없는 고유명사(지명·인명)는 복원 못 한다** — 자서전에서
  지명·인명은 핵심이므로, 자녀/부모가 이름만 고치는 가벼운 교정 UI가 후처리의 보완재다.
- 우리 지연 허용치(하루 단위)에선 후처리를 **배치로 밤사이** 돌리면 되고, 후처리는
  오류 교정 + 간투사 제거 + 문단화 + (선택) 후속 질문 생성을 한 호출로 겸한다.
- 비용은 미미하다: 답변 1건당 입력 ~700토큰·출력 ~400토큰 `추정`, 하이쿠급
  ($1/$5 per MTok — claude-api 스킬 캐시 2026-06) 기준 **건당 ~4원**.

### A-6. 판정 — **조건부 Go**

- **Go 근거**: 배치 STT 단가 4~20원/분 + LLM 후처리 건당 ~4원 → 원가 구조 성립(아래 표).
  파이프라인 기술도 검증된 조합(Remento의 Speech-to-Story가 동일 구조 —
  [Remento FAQ](https://www.remento.co/faq)).
- **조건**: A-3의 실측 파일럿(1~2일)에서 고령자·사투리 샘플 CER이 실용 범위
  (제안 기준: **후처리 후 사람이 "고칠 데가 한두 군데" 수준, CER ~10% 이하 `추정 기준`**)로
  확인될 것. 실패 시 폴백: 파인튜닝(AI Hub 노인 데이터로 Whisper 계열) 또는
  국내 업체 커스텀 계약 — 둘 다 MVP 이후 과제다.

**권고 스택 1개**: **리턴제로 RTZR 배치 STT + 하이쿠급 LLM 후처리.**
(공개 벤치 1위 + 한국어 자유발화 특화 + 종량 단가 명확. 단 실측 파일럿에서
gpt-4o-transcribe와 반드시 맞대결시켜 — 품질이 비슷하면 1/4 가격인 OpenAI로 간다.)

**월 비용 추정 — 사용자(부모) 1,000명 가정:**

```
가정: 일 응답률 60% `추정`(G2 목표 상회 가정) × 평균 답변 2분 `추정`
→ 월 음성 1,000명 × 30일 × 60% × 2분 = 36,000분, 답변 18,000건
```

| 스택 | STT | LLM 후처리 | 합계/월 |
|---|---|---|---|
| **권고: RTZR + 하이쿠급** | 36,000분 × 16.7원 ≈ 60만 원 | 18,000건 × 4원 ≈ 7만 원 | **약 67만 원 `추정`** |
| 대안: gpt-4o-mini-transcribe + 하이쿠급 | 36,000분 × 4.1원 ≈ 15만 원 | ≈ 7만 원 | 약 22만 원 `추정` |
| 참고: 클로바 스피치 + 하이쿠급 | 36,000분 × 20원 ≈ 72만 원 | ≈ 7만 원 | 약 79만 원 `추정` |

BUSINESS_CASE §6-A 현실 시나리오(유료 1,500건, 월 매출 ~1,050만 원) 대비
권고 스택 원가는 매출의 ~6% — **공헌이익률 65% 가정을 깨지 않는다.**
(주의: 위 표는 "유료 사용자 1,000명 전원 활성" 가정이라 보수적이다.)

## B. 응답 경로 실현성 (R3)

### B-1. 경로 ① — 부모용 네이티브 앱 (RN/Expo) : **표준 경로, 기술 리스크 낮음**

- 필요한 것 전부가 팀 선례 스택 범위: 푸시(expo-notifications + FCM/APNs),
  음성 녹음(expo-av/expo-audio), 큰 글씨 UI(디자인 시스템), Firebase 백엔드.
- **설치 장벽의 실체는 기술이 아니라 절차다.** 완화 설계(§4-3의 R3 요건과 일치):
  - **자녀가 결제 시 초대 링크 생성 → 부모 폰에서 링크 한 번 = 로그인 완료**
    (익명 인증 + 초대 코드 바인딩 — 부모의 회원가입·비밀번호 없음. ONYU 방식).
  - 명절 귀성 때 자녀가 대리 설치하는 "구매~활성화 시차"는 PM 범위(§4-3)로 이관.
  - 스토어 설치 자체는 없앨 수 없다 — 이것이 ①의 유일한 구조적 약점.
- 배포 경로 유의(OTA_AND_BUILDS 플레이북): 녹음·푸시는 **네이티브 모듈이라
  개발 빌드 필수**, 마이크 권한 문구는 OTA로 못 바꾼다. 첫 빌드 전에 권한 문구·
  scheme(초대 딥링크용)을 확정하고 시작해야 빌드 예산을 아낀다.
- 개발 크기: 부모 플로우(푸시→질문→녹음→업로드) + 자녀 플로우(구독·열람·반응) +
  서버(질문 발송 스케줄·STT 파이프) = **6~8주 `추정`** (1 APP + 1 BE 병렬 기준).

### B-3. 경로 ③ — 하이브리드 (알림톡으로 부르고, 웹/앱에서 답하기) : **성립하나 MVP엔 과함**

- 기술적으로 성립: 알림톡 템플릿은 **WL(웹링크)·AL(앱링크) 버튼**을 지원한다 —
  버튼 한 번으로 모바일웹 녹음 페이지 또는 앱 딥링크 진입
  ([솔라피 버튼 유형 가이드](https://guide.solapi.com/e8d99bdf-eb1c-4e53-b5b3-d2e558ab69f1)).
- 리스크 2개:
  - **웹 녹음의 인앱 브라우저 함정**: 알림톡 링크는 카톡 인앱 브라우저에서 열리는데,
    인앱 브라우저의 마이크(getUserMedia) 권한 동작이 기기·OS별로 불안정할 수 있다
    `미확인` — 채택 전 실기기 검증 필수(iOS 카톡 인앱 + Android 웹뷰 각각).
  - 웹 녹음 페이지는 앱과 별개 표면이라 **개발·QA 폭이 늘어난다** (+2~3주 `추정`).

  알림톡으로 재호출 → 앱 딥링크(AL 버튼). 이때 알림톡은 "가입자 대상 서비스 알림"이라
  정보성 성립 여지가 크다 `추정`. 월 발송량도 전체가 아니라 이탈 위험군만이라 비용이 준다.

### B-4. 판정 — MVP 권고 경로

**권고: ① 네이티브 앱 (자녀 대리 설치 + 초대 링크 원터치 로그인).**

| | ① 앱 (권고) | ② 카카오 단독 | ③ 하이브리드 |
|---|---|---|---|
| 음성 답변 | 가능 (핵심 요건) | **불가** (챗봇 음성 수신 경로 없음) | 웹 녹음 — 인앱 브라우저 리스크 `미확인` |
| 온보딩 장벽 | 설치 필요 (자녀 대리로 완화) | 없음 (카톡 그대로) | 낮음 |
| 정책 리스크 | 스토어 심사만 | 알림톡 심사 + 정책 변동 상시 | 알림톡 심사 |
| 매일 알림 비용 | 푸시 무료 | 월 24만~42만 원 (1,000명) | 이탈군만 발송 시 소액 |
| 개발 크기 `추정` | 6~8주 | 2~3주 (단, 텍스트 온리) | ① + 2~3주 |

이유: 이 제품의 유일한 차별점 결합(BUSINESS_CASE §5 — 데일리 습관 × 자녀 피드백 루프
× 책)에서 **음성은 빠질 수 없는 다리**고, 음성을 받을 수 있는 경로는 ①과 ③뿐이다.
③은 ①을 만든 뒤에만 의미가 있는 보조 채널이므로, MVP는 ①이다. ②의 장점(설치 제로)은
①의 초대 링크 설계로 절반쯤 흡수한다.

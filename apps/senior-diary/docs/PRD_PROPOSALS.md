## 아이디어 1 — 입력 방식 선택(녹음/타자) + 실시간 화면 STT

### 무엇을
부모가 답할 때 **녹음(기본) / 타자로 직접 쓰기**를 고르게 한다. 녹음을 고르면
**말하는 동안 STT가 화면에 실시간으로 뜬다**(정리·확인).

### 왜 좋은가
- **타자 선택**: PRD P2(§1-2)에서 타이핑은 시니어 장벽이라 음성 우선으로 갔지만,
  일부 부모(글 선호·조용한 환경 필요·발화 부담)에게는 타자가 오히려 낮은 문턱이다.
  "음성만"은 우리가 세운 가정이지 검증된 사실이 아니다 — 선택지는 그 가정의 보험이다.
- **실시간 자막**: "내 말이 담기고 있다"는 즉각 피드백이 **불안(녹음이 되나?)을
  없애고** 발화를 이어가게 한다 — 원칙 3(기록됨의 실감)을 강화.

### 기존 설계와의 충돌 / 정합
- **핵심 긴장 (실시간 vs 밤사이):** 현재 I3·§3-5는 **"로컬은 녹음만 → 밤사이 배치
  STT+LLM 문학적 정리 → 다음날 정리본"**이다. 이 설계의 *의도된 이유*가 있다(스파이크
  §A-4·§A-2): ① 실시간 받아쓰기는 **오인식이 화면에 그대로 보여 시니어를 위축**시킨다
  ("녹음만 하세요, 정리는 밤사이"가 올바른 UX라는 스파이크 판단), ② 내장 실시간 STT는
  1분 세션 제한·침묵 자동종료가 있어 1~3분 발화와 충돌. **즉 실시간 표시는 우리가
  일부러 하지 않기로 한 것과 정면으로 만난다.**
- **BE 스파이크의 2단계안(BE 확인 대기):** `SPIKE_REALTIME_STT_WEB.md`가 **①실시간
  러프 자막(확인용, 문학적 아님) → ②밤사이 문학적 정리(정본)**의 2단계로 공존
  가능성을 검토 중. 이 판정이 나오기 전까지 실시간 표시의 실현성·품질·원가는 미정 —
  **"BE 확인 대기"**. 특히 검증할 것: 러프 자막이 시니어를 위축시키지 않게 만들 수
  있는가(스파이크 §A-4 우려의 정면 반박이 되는가), 응답 경로 B안(네이티브 앱)에서
  실시간 스트리밍 STT의 단가·지연.
- **타자 선택은 충돌 없음:** 답변 개체(§IA §4 ANS)는 이미 "원음+정리본"이고, 타자는
  "원음 없는 정리본"으로 자연스럽게 들어온다. 밤사이 정리 파이프라인(§3-5)도 타자
  입력은 STT를 건너뛰고 LLM 정리만(또는 그대로) 태우면 된다.

### 범위 (appetite)
- **타자 선택 (소):** P2에 입력 모드 토글 + 텍스트 입력 화면. 데이터 모델 무변경.
  → 6주 목표 안에 흡수 가능 `추정`. 단 §3-2에서 "흡수 여유 소진" 선언했으므로
  **등가 축소 필요**(예: I9 책 미리보기를 정적 1페이지로 축소).
- **실시간 자막 (중~대):** 스트리밍 STT 배선 + 실시간 자막 UI + 시니어 접근성(자막
  글자 크기·스크롤·오인식 심리). **6주 안에 안 들어온다** — 별도 에픽.

### 의존성
- 실시간: **`SPIKE_REALTIME_STT_WEB.md` 판정(BE, 작성 중)** · G4 실측(BACKLOG S2.5) ·
  실 STT 스택(S2.4). 타자: PD(입력 화면·키보드 회피 — BACKLOG "미검증" 목록에 이미 있음).

### PRD / IA 어디가 바뀌나 (승인 시)
- PRD: §1-2 P2(타이핑 장벽 서술에 "선택지로 보험" 추가), §3-1 **I3 개정**(입력 방식
  선택 명시), §3-5 매일 단계(타자 경로 분기), §3-7 구현 현황(실시간=신규 TODO).
- IA: §4 답변 개체(원음 유무 분기), §5-1 답변 생애(타자는 "녹음됨" 상태 건너뜀),
  §2 P2 화면(모드 토글). 실시간은 P2에 새 상태(자막 스트림) 추가.
- BRAND §3-B: 타자 입력 화면의 마이크로카피 신규(용어집 "직접 쓰기").

### PO 결정 필요
1. 타자 선택을 MVP 베타에 넣는가(등가 축소 1건 감수)? 2. 실시간 자막을 로드맵 어디에
두는가(BE 스파이크 판정 후 재상신 예약)?

### **PM 권고 — 분할**
- **입력 방식 선택(녹음/타자): MVP 검토 권고.** 저비용이고 "음성만" 가정의 보험이라
  G2(지속) 리스크를 줄인다. 단 appetite 여유가 없어 **등가 축소를 함께 상신**한다.
- **실시간 화면 STT: V1.x — 지금 결정 보류.** 우리가 의도적으로 피한 UX(오인식 노출)와
  정면으로 만나고, 실현성이 **BE 스파이크 미판정**이다. 스파이크 2단계안이 "시니어
  위축 없이 러프 자막이 가능"으로 닫히면 그때 재평가. G2 검증에 실시간은 **불필요**
  하다(밤사이 정리로도 습관·루프는 측정된다) — MVP에 넣을 근거가 약하다.

## 아이디어 2 — 질문에 자녀 이름 섞기 / 인터뷰 느낌

### 무엇을
질문을 배달할 때 자녀 이름을 섞어 **자녀가 직접 여쭙는 인터뷰 느낌**을 준다.
예: "지혜가 여쭤요 — 처음 서울에 올라오시던 날, 기억나세요?"

### 왜 좋은가
- **원칙 2(자녀의 반응&응원)를 매일 아침으로 확장.** 지금 자녀 존재감은 응원이 올
  때만 느껴진다(사후). 질문에 이름을 얹으면 **매일의 질문 자체가 자녀의 목소리**가
  되어, 부모가 답할 동기(누가 궁금해하는가)가 선명해진다 — R2(지속) 완화에 직접 기여.
- 마이마더스토리(연결 루프만 있고 습관 없음)와의 차이를 **질문 단계에서부터** 벌린다.

### 기존 설계와의 충돌 / 정합
- **정합 (강):** BRAND §3-B가 이미 자녀 이름을 쓴다 — "지혜님이 응원을 보냈어요 💛".
  프로필 폼(I1)에 자녀 이름·호칭이 이미 수집된다(IA §4 PROFILE). 룰 분기 엔진(I2,
  `branching`)은 이미 프로필 조건으로 질문을 치환하므로, **이름 토큰 삽입은 같은
  엔진의 문자열 치환**이다 — 새 시스템이 아니다.
- **긴장 (해결 필요 1건):** BRAND §3-B는 부모 화면 질문의 화자를 *"곁에서 대신
  여쭙는 사람"*으로 두고 **서비스 주체를 드러내지 않는다**("여쭤볼게요"). 아이디어 2는
  화자를 **자녀 본인으로 명시 전환**한다("지혜가 여쭤요"). 둘 다 좋은 방향이지만
  **화자 규칙이 갈리므로 BRAND가 정본을 다시 못박아야 한다** — 상시 자녀 화자로
  갈지, 가끔(주 1회 등)만 자녀 화자로 강조할지. 남용하면 인터뷰 연출이 피로해질 수
  있다 `추정` → **빈도·톤 규칙이 필요.**
- 데이터·리스크: 자녀 이름은 이미 있으니 신규 수집 없음(R4 개인정보 증가 없음).

### 범위 (appetite)
- **소.** 질문 템플릿에 `{childName}` 토큰 + 삽입 룰(빈도·존대 처리) + 뱅크 문구
  일부에 인터뷰형 변형. 엔진 무변경. → 6주 안에 흡수 가능, 등가 축소 불요 수준 `추정`.

### 의존성
- **BRAND**(화자 규칙 §3-B 개정 — 정본) → PM/PD(질문 뱅크 문구, BACKLOG E5) →
  APP(토큰 치환은 `branching`에 이미 자리 있음).

### PRD / IA 어디가 바뀌나 (승인 시)
- PRD: §3-1 **I2 개정**(이름 토큰·인터뷰 변형 명시), §0-1 원칙 2 연결 강화.
- IA: §4 오늘의 질문 개체 서술(이름 바인딩), 화면 변화는 문구뿐(구조 무변경).
- BRAND: §3-B 화자 규칙 **개정(정본)** + §3-A 슬로건 체계와의 톤 정합.

### PO 결정 필요
1. 자녀 화자를 **상시**로 할지 **선택적 강조**로 할지. 2. BRAND에 화자 규칙 개정 착수 승인.

### **PM 권고 — MVP 넣기 권고**
저비용·고정합이고, **원칙 2를 매일로 끌어와 G2(지속)에 직접 기여**한다. 이미 있는
데이터(자녀 이름)와 이미 있는 엔진(룰 치환) 위에 얹히므로 appetite 부담이 가장 작다.
**단 조건: BRAND가 화자 규칙(§3-B)을 먼저 정리**(상시 vs 선택적)해야 PD 문구가 갈라지지
않는다 — BRAND → PD 파생 순서(TEAM.md §3). 이 1건만 선행하면 MVP 베타에 넣기 좋다.

## 아이디어 3 — 웹소설 뷰어 중간 확인 + 디지털/인쇄 가격 분리

### 무엇을
"1년 뒤 서프라이즈"만으로는 축적 기간이 너무 길다. **주/월/목차 단위로 엮인 결과를
웹소설 뷰어처럼 중간에 상시 읽기.** 물성(인쇄) 책은 마일스톤/서프라이즈로 재배치.
**BM: 디지털 상시 읽기 = 기본 유료에 포함 / 오프라인 인쇄 책 = 별도 추가 구매.**

### 왜 좋은가
- **원칙 4(책 완성)의 "너무 긴 보상 지연" 문제를 정확히 짚는다.** 지불한 자녀가 1년을
  기다려야 가치를 처음 본다면 이탈·환불(K4) 위험이 크다. 중간 읽기는 **보상을 앞으로
  당겨** 자녀의 재방문(원칙 2)과 부모의 지속(원칙 1)을 동시에 끌어올린다.
- 이미 이 방향의 씨앗이 제품에 있다 — I5 모아보기(C5)·I9 책 미리보기(C6). 아이디어 3은
  이걸 **"미리보기 샘플"에서 "상시 읽는 뷰어"로 격상**하는 것이다.

### 기존 설계와의 충돌 / 정합
- **정합 (강):** IA §2에 C5(모아보기)·C6(책 미리보기)가 이미 있고, §3-5는 "챕터
  구조가 곧 목차"라 **주/월/목차 단위 묶음이 데이터 상 이미 가능**하다. 뷰어는 C6를
  "샘플 정적 화면"에서 "챕터별 펼쳐 읽기"로 확장하는 것 — 새 개체가 거의 없다.
- **차별화 4요소 재조정:** 원칙 4 "1년 뒤 책"을 **"디지털은 상시 읽기 + 물성 책은
  마일스톤"**으로 재정의. 이는 BUSINESS_CASE §0 보도자료("1년 뒤 책이 도착")의 정서를
  **약화**시킬 수 있다 — 서프라이즈성이 희석될 위험. 반대로 "쌓이는 게 매주 보인다"는
  리텐션 이점이 그것을 상쇄하는지는 **G2에서만 판별**된다.
- **가격 구조는 PM 소관이 아니다:** 디지털 포함/인쇄 별도의 BM 함의(가격탄력성·업셀
  전환·원가)는 **BD가 `PLATFORM_BM_ANALYSIS.md`에서 병렬로** 다룬다(작성 중, 참조).
  PM은 기능·IA·리텐션 관점까지만. D5(가격 3안)·§3-4 O1(결제)과 직접 얽힌다.

### 범위 (appetite)
- **뷰어 확장 (중):** C6를 챕터별 펼쳐 읽기로 + 주/월 묶기 로직 + 새 읽기 상태(어디까지
  읽음). 6주 목표엔 **전체는 안 들어온다.** 단 **축소형은 이미 있다** — I5/C5 진행감 +
  I9/C6 미리보기가 "중간에 쌓인 걸 본다"의 최소형이다.
- **가격 모델: appetite 밖(PO·BD).**

### 의존성
- **BD `PLATFORM_BM_ANALYSIS.md`**(가격 구조) · **PO D5**(가격) · PD(뷰어 화면) ·

## 0. 요약 (한 문단)

한국 천주교 신자에게 필사 기능은 **이미 있다**(CBCK 공식 앱 '가톨릭(굿뉴스)').
없는 것은 **그 필사를 매일 이어가게 하는 경험**이다. Lectio는 기능을 더 얹는
제품이 아니라, "오늘 무엇을 쓸지 고르는 마찰"과 "앱을 열어야만 존재하는 습관"
두 가지를 없애는 제품이다. 하루 한 구절, 4~7분, 홈화면 위젯과 한 번의 알림.
전례 시기가 앱의 색과 문장을 바꾸고, 필사한 뒤 한 줄 성찰이 내 노트에 쌓인다.
성경 본문은 앱이 소유하지 않고 원격 콘텐츠 팩으로 주입한다 — 저작권 승인 절차와
제품 개발을 분리하기 위해서다.

## 1. 문제 정의

### 1-1. 누구의 무슨 문제인가

> **공식 앱이 이미 있고 무료인데도 왜 남는 문제가 있는가** — 이 질문에 답하지
> 못하면 이 제품은 만들 이유가 없다. 아래가 답이다.

전제로 삼는 사실(오케스트레이터 조사, 재검증 불필요):
CBCK 공식 앱 '가톨릭(굿뉴스)'에는 매일성경쓰기 / 개인성경쓰기 / 클럽성경쓰기 /
성경쓰기 통계가 **이미 있다**. 무료다. 다만 App Store 평점 3.6(리뷰 350),
최종 업데이트 2024-09, 리뷰 불만은 "여러 프로그램을 하나로 통합해 난해하다",
"화면이 겹쳐 신청을 못 한다", 날짜 선택 제한에 몰려 있다.

즉 우리의 빈틈은 **"필사 기능이 없다"가 아니라 "지속시키는 경험이 없다"**이다.
문제를 네 개로 쪼갠다.

| # | 문제 | 지금 어떻게 되고 있나 | 지속에 미치는 영향 |
|---|---|---|---|
| P1 | **시작 마찰** | 통합 앱이라 오늘 쓸 것 하나에 닿기까지 메뉴를 여러 번 거친다. "뭘 쓸지 고르는" 결정이 매일 반복된다 | 결정 피로 → 3일째에 안 연다 |
| P2 | **상기(想起) 표면의 부재** | 앱을 스스로 열어야만 습관이 존재한다. 홈화면에 오늘의 상태가 보이지 않는다 | 습관 형성의 단서(cue)가 없다 |
| P3 | **남는 것이 없음** | 통계 숫자는 쌓이지만 "내가 쓴 말씀"과 "그때 무엇을 느꼈는지"가 되돌아볼 형태로 남지 않는다 | 지속의 보상이 숫자뿐 → 숫자가 끊기면 이유가 사라진다 |
| P4 | **전례 맥락의 단절** | 오늘이 전례력의 어디인지(대림 2주 화요일인지, 사순 중인지)와 필사가 이어지지 않는다 | 가톨릭 신자에게 가장 자연스러운 "오늘의 이유"를 못 쓴다 |

### 1-2. 우리가 하지 않을 싸움

- **성경 열람 앱을 만들지 않는다.** 전권 검색·본문 열람은 공식 앱이 이미 낫고
  저작권상으로도 우리가 이길 수 없는 영역이다.
- **공동체(클럽)로 정면충돌하지 않는다.** 클럽성경쓰기는 공식 앱의 강점이자
  본당 조직과 결합돼 있다. V1은 **개인의 하루**에만 집중한다 (§3 뺄 것).
- **미사 시간·성당 찾기·교리 자료로 확장하지 않는다.** 통합 앱이 난해해진
  경로를 그대로 밟는 일이다.

### 1-3. 가치 가설 (검증 대상)

> 하루 한 구절을 **직접 옮겨 쓰는 4~7분**을, **홈화면 위젯 + 하루 한 번의
> 알림**이 상기시키면, 신자는 앱을 스스로 여는 것보다 오래 습관을 유지한다.

이 가설이 **위젯·알림을 요구하기 때문에** V1은 미니앱/웹이 아니라 네이티브 앱이다.
(미니앱은 유입 표면으로 V1.x 이후 검토 — §3 뺄 것)

## 2. 타깃 세그먼트와 사용 맥락

### 2-1. 세그먼트

시장 사실: 신자 600만(인구 11.4%), 증가율 0.2%로 둔화, 65세 이상 28.9%,
교적 신자 중 주일미사 참여 15%, 청년 신자 감소.
→ **"청년"만 겨냥하면 시장이 너무 작다.** 다음과 같이 나눈다.

| | 세그먼트 | 규모감 | V1 우선순위 | 왜 |
|---|---|---|---|---|
| **S1** | **35~59세 실천 신자, 여성 다수.** 본당·구역 활동 참여, 매일미사 책자·묵상집을 이미 쓰고 있음. 스마트폰 능숙 | 가톨릭 앱 실사용층의 다수 | **주 타깃** | 이미 "매일 무언가를 읽는 습관"이 있다. 우리는 습관을 만드는 게 아니라 **옮겨오면** 된다 — 가장 싼 획득 |
| **S2** | **25~34세 신자 / 냉담 회복 중 / 예비신자.** 주일미사는 띄엄띄엄, 신앙과 다시 연결될 저부담 접점을 찾는 층 | 작지만 성장 여지 | **부 타깃** | 미사 참여라는 큰 문턱 대신 **하루 5분**이라는 낮은 문턱. WYD 2027 유입이 정확히 이 층이다 |
| **S3** | **60세 이상 신자** | 가장 큼 | **타깃 아님. 단, 배제하지 않음** | V1의 핵심 상호작용이 타이핑/필기라 신체 부담이 크고, 획득 채널도 다르다(본당 오프라인). 그러나 **큰 글씨·고대비·최소 탭 수는 V1에서 지원**한다 — S1의 부모 세대가 자연 유입되는 경로를 막지 않기 위해서다 |

**세그먼트를 이렇게 잡은 이유(PO 확인 요망):** S1을 주 타깃으로 두면 WYD 훅
없이도 제품이 성립한다. WYD는 S2를 밀어 넣는 시즌 이벤트일 뿐이다 (§3, §10-E).

### 2-2. 사용 맥락 (언제·어디서·몇 분)

| | 주 맥락 A | 주 맥락 B |
|---|---|---|
| 언제 | **기상 직후 06:00~08:00** | **취침 전 21:00~23:00** |
| 어디서 | 집, 침대/식탁. 한 손 또는 두 손 | 집, 침대. 조명 어두움 |
| 자세 | 앉음. 조용함 | 누움/기댐 |
| 목표 시간 | **4~7분** (구절 필사 3~5분 + 성찰 1~2분) | 같음 |
| 설계 요구 | 첫 화면에서 **탭 1회**로 필사 시작 | **다크 모드 기본 대응**, 흰 배경 눈부심 금지 |

보조 맥락 C: 출퇴근 지하철(서서, 흔들림, 한 손) — V1은 **최적화하지 않는다.**
필사는 정지 상태의 행위다. 다만 이 맥락에서 앱을 열었을 때 "나중에 하기"가
막다른 길이 되지 않게, 위젯/알림 재-리마인드로 회수한다.

**세션 설계 상한: 7분.** 렉시오 디비나 4단계를 매일 전부 시키면 이 상한을 넘긴다
→ V1은 4단계 중 2단계만 필수로 한다 (§4-0).

### 3-3. 전제와 제약 (설계 이전에 고정된 것)

| # | 제약 | 설계에 미치는 영향 |
|---|---|---|
| C1 | **한국 가톨릭 「성경」(2005) 저작권은 CBCK 소유.** 성경 30% 초과 사용 시 별도 승인 필요. 앱은 출판물로 간주되어 **승인 신청 대상.** **유료 배포는 계약 체결이 원칙** | ① 본문을 앱 번들·저장소에 넣지 않는다 (§6-3) ② 누적 인용 총량을 발행 파이프라인에서 계량한다 (§6-4) ③ **V1은 무료 배포를 전제한다** — 유료화는 계약 이슈를 즉시 불러온다 (§10-C) ④ 승인 철회 시 **앱 재제출 없이 본문만 회수**할 수 있어야 한다 (§6-5 킬 스위치) |
| C2 | 승인 절차가 개발 일정보다 길 수 있다 | **저작권 승인 없이도 개발·내부 테스트가 끝까지 진행되는 구조**여야 한다 → 콘텐츠 공급자 추상화 + 개발용 플레이스홀더 팩 (§6-3) |
| C3 | 전례력·축일명·독서 배치(가나다 주년/홀짝 주간)는 **사실 정보**로 본문 저작물과 성격이 다르다 | 전례력 데이터는 앱 번들에 포함 가능. **본문만** 원격 주입 (§6-2) |
| C4 | iOS 위젯은 입력 불가, 갱신 주기도 시스템이 통제한다 | 위젯은 **표시 + 딥링크 전용**. 갱신 실패 시의 표시 상태를 반드시 정의한다 (§5-1) |
| C5 | 알림 권한은 거부될 수 있고, 한 번 거부되면 앱 내에서 되돌릴 수 없다 | 권한 요청 타이밍 설계 + 거부 상태에서도 제품이 성립하는 경로 (§4-S10, §5-2) |
| C6 | 팀 규칙: 비가역 행동(제출·배포)은 PO 승인 후에만 | 이 PRD 자체가 PO 승인 전에는 구현으로 넘어가지 않는다 |

## 4. 화면 흐름 + 텍스트 와이어프레임

> **오류 상태를 명세하지 않은 화면은 미완성이다** (PD 하네스).
> 모든 화면에 로딩 · 빈 · 오류 · 권한 거부 · 오프라인 상태를 적는다.
> 해당 없는 상태는 "해당 없음"이라고 **적는다** — 빈칸으로 두지 않는다.

### 4-0. 렉시오 디비나 4단계를 V1에 넣는 방식

| 전통 단계 | V1 대응 | 필수 여부 | 소요 |
|---|---|---|---|
| Lectio (독서) | **필사** — 옮겨 쓰는 행위 자체가 느린 독서다 | 필수 | 3~5분 |
| Meditatio (묵상) | **한 줄 성찰** — "오늘 이 말씀에서 마음에 남은 것" 1문장 | 필수(건너뛰기 가능) | 1~2분 |
| Oratio (기도) | **머무는 시간** — 화면에 아무것도 없는 60초 | 선택(기본 꺼짐) | 1분 |
| Contemplatio (관상) | 위와 통합. **별도 단계로 쪼개지 않는다** | — | — |

**왜 4단계를 다 안 시키는가:** 세션 상한 7분(§2-2)을 넘기면 습관이 안 붙는다.
4단계를 전부 강제하는 앱은 "제대로 하는 앱"이 아니라 "3일 만에 지치는 앱"이다.
단, **설정에서 "머무는 시간"을 켜면 4단계가 완성되도록** 설계한다 — 깊이를 원하는
사용자에게 길이 열려 있어야 한다.

### 4-1. 전체 흐름

```
[최초 실행]
  S0 온보딩 (4스텝) ──► S1 오늘

[매일]
  위젯 탭 ─┐
  알림 탭 ─┼─► S1 오늘 ──[지금 필사하기]──► S2 필사 ──► (S3 머무는 시간, 선택)
  앱 아이콘┘                                            └──► S4 성찰 한 줄
                                                              └──► S5 완료
                                                                    └─► S1 오늘(완료 상태)
[언제든]
  S1 ──► S6 기록 ──► S7 기록 상세
  S1 ──► S8 설정 ──► S9 위젯 안내 / S10 알림 설정
```

**딥링크 표** (위젯·알림이 어디로 보내는가)

| 링크 | 목적지 | 오늘 이미 완료했으면 |
|---|---|---|
| `lectio://today` | S1 오늘 | S1 (완료 상태로 표시) |
| `lectio://write` | S2 필사 (바로 시작) | S7 오늘 기록 상세로 대체 |
| `lectio://record?date=YYYY-MM-DD` | S7 기록 상세 | — |

> 딥링크가 "이미 완료한 날의 필사 화면"으로 가서 **같은 날 두 번 쓰게 만드는 일이
> 없도록** 라우팅 단계에서 완료 여부를 먼저 판정한다 (§7-B).

### S2. 필사

> 입력 방식(타자 / 손글씨 / 둘 다)은 **§10-A에서 PO가 결정한다.**
> 아래 와이어프레임은 **A안(타자)** 기준이며, B안 채택 시 입력 영역만 교체된다.
> 그 외 구조(상단 출처, 진행 표시, 완료 판정, 상태 명세)는 안과 무관하게 동일하다.

```
┌──────────────────────────────────────┐
│ ✕                        요한 13,35  │  ← 나가기 / 출처(항상 보임)
│ ────────────────────────────────────  │
│                                      │
│   너희가 서로 사랑하면, 모든 사람이   │  ← 원문 (연한 회색, 읽기용)
│   너희를 나의 제자라고 알아볼 것이다. │
│                                      │
│ ────────────────────────────────────  │
│                                      │
│   너희가 서로 사랑하면, 모든 사람이   │  ← 내가 쓴 것 (진한 색)
│   너희를 나의 제자라고 알아볼 것이_   │
│                                      │
│                                      │
│  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░  ← 진행 (길이 기준, 채점 아님)
│                                      │
│  ┌────────────────────────────────┐  │
│  │          다 썼습니다            │  │  ← 완료 (비활성→활성)
│  └────────────────────────────────┘  │
│ ────────────────────────────────────  │
│ [키보드]                             │
└──────────────────────────────────────┘
```

**필사 화면의 설계 규칙 (안 A/B 공통)**

1. **채점하지 않는다.** 오타를 빨간 줄로 표시하지 않는다 (X12). 진행 표시는
   "얼마나 남았나"의 안내지 정확도 점수가 아니다.
2. **완료 버튼 활성 기준**: 입력 길이가 원문 길이의 **80% 이상**이면 활성.
   내용 일치는 검사하지 않는다. (80%라는 수치는 사용자에게 노출하지 않는다 —
   내부 수치를 문구에 넣지 않는다, PD 하네스 규칙표)
3. **자동 저장**: 3초마다 + 앱 백그라운드 진입 시 즉시 초안 저장. 앱이 죽어도
   돌아오면 이어 쓴다.
4. **나가기(✕)**: 입력이 있으면 확인 시트 — "쓰던 것을 저장하고 나갈까요?"
   [저장하고 나가기] [계속 쓰기]. **[삭제]는 두지 않는다** (되돌릴 수 없는 행동을
   실수 한 번으로 만들지 않는다)
5. **아날로그 감각 장치** (A안 채택 시 반드시 함께 구현): 종이 질감 배경, 세리프
   본문 서체, 입력 시 미세한 촉각 피드백, **자동완성·맞춤법 교정 끄기**
   (`autoCorrect=false`, `spellCheck=false`, `keyboardType=default`).
   → 자동완성이 켜져 있으면 "옮겨 쓰는" 감각이 "타이핑"으로 무너진다.

| 상태 | 명세 |
|---|---|
| **로딩** | S1에서 이미 본문을 갖고 진입하므로 로딩 없음. 본문 없이 딥링크로 직접 진입한 경우만 스켈레톤 → 실패 시 S1으로 되돌리고 S1의 오류 상태를 보여준다 |
| **빈** | 입력 0자: 완료 버튼 비활성 + 내 영역에 플레이스홀더 "여기에 옮겨 씁니다" (1회, 첫 글자 입력 시 사라짐) |
| **오류 — 저장 실패** | `쓰신 내용을 저장하지 못했습니다. (draft.save_failed)` 배너 + 자동 재시도. **입력을 계속할 수 있게 둔다** — 저장 실패로 화면을 막지 않는다 |
| **오류 — 기기 저장공간 부족** | `저장공간이 부족합니다. (storage.full)` + [설정 열기]. 손글씨(B안) 채택 시 발생 확률이 훨씬 높다 → §10-A 트레이드오프 항목 |
| **권한 거부** | A안(타자): 해당 없음. B안(손글씨): 사진 앨범 저장 권한 거부 시 → 앱 내부에만 저장하고 [이미지로 내보내기]만 비활성 + 사유 툴팁 |
| **오프라인** | **완전히 정상 동작.** 필사는 네트워크를 쓰지 않는다. 이 화면에 네트워크 의존을 넣지 않는 것이 규칙이다 |

## 5. 위젯 · 알림 사양

### 5-1. 위젯

| 크기 | 표시 내용 | 탭 → |
|---|---|---|
| **systemSmall** | 전례 시기 색 배경 · 오늘 완료 여부(✓ 또는 빈 원) · 구절 **첫 줄 8~12자 + …** · 출처 | 미완료 → `lectio://write` / 완료 → `lectio://record?date=today` |
| **systemMedium** | 좌: 전례일 + 완료 여부 + 주간 도트 / 우: 구절 2~3줄 + 출처 | 좌측 영역 → `lectio://today` / 우측 구절 영역 → `lectio://write` |
| **systemLarge** | 전례일 + 축일 + 구절 전문 + 출처 + 주간 도트 | `lectio://write` (완료 시 `record`) |
| **accessoryRectangular** (잠금화면) | 출처 + 구절 첫 줄 (단색) | `lectio://today` |
| **accessoryCircular** (잠금화면) | 주간 진행 링 + 오늘 ✓/○ | `lectio://today` |

**위젯 규칙**

1. **위젯에서 본문 전문을 보여주는 것은 systemLarge뿐이다.** small/medium은 발췌.
   → 저작권 노출 총량 관리(§6-4)와 "앱을 열게 만드는" 설계 양쪽의 이유.
2. **갱신**: 자정(로컬 04:00 경계, §7-A) + 앱에서 완료 시 즉시(`reloadTimelines`).
   iOS가 갱신을 미룰 수 있으므로 타임라인은 **다음 3일치를 미리 만들어 둔다.**
3. **App Group 공유 저장소**로 앱↔위젯이 데이터를 주고받는다. 위젯은 네트워크를
   직접 치지 않는다 (§6-2).

| 위젯 상태 | 표시 |
|---|---|
| **정상** | 위 표대로 |
| **로딩(첫 설치 직후, 데이터 없음)** | 전례 시기 색 + 앱 이름 + "앱에서 오늘의 구절을 받아옵니다" (1회성). 탭 → `lectio://today` |
| **빈 — 오늘 본문 없음** | 전례일 + "오늘 본문이 준비되지 않았습니다" |
| **오류 — 데이터가 낡음(3일 이상 갱신 안 됨)** | 마지막으로 받은 구절을 **보여주되** 출처 옆에 옅은 날짜 표기(예: `8월 10일`) → 사용자가 낡은 것임을 알 수 있게. **틀린 날짜를 오늘인 척 보여주지 않는다** |
| **오류 — 본문 회수됨** | 전례일 + 출처(장절)만. 본문 영역은 비운다 |
| **권한 거부** | 해당 없음 |
| **오프라인** | 캐시로 정상 동작 |

### 5-2. 알림

| 항목 | 사양 |
|---|---|
| **주 알림** | 하루 1회. 사용자 지정 시각(기본 07:00). 로컬 알림(서버 푸시 없음 — X1/X2와 일관) |
| **저녁 회수 알림** | **기본 꺼짐.** 켜면 사용자 지정 시각(기본 21:00)에, **오늘 미완료일 때만** 1회 |
| **최대** | **하루 2회를 절대 넘지 않는다.** 연속기록·주간 목표를 이유로 추가 알림을 보내지 않는다 |
| **예약 방식** | iOS 로컬 알림 예약 상한(64개)을 고려해 **14일치를 롤링 예약**, 앱 포그라운드 진입 시마다 재충전 |
| **본문 인용** | 알림 문구에 **구절 첫 12자까지만** 인용 + 출처. 전문 금지 (§6-4) |

**알림 문구 원칙 (§9와 함께 강제)**

| 원칙 | ✅ 쓴다 | ❌ 안 쓴다 |
|---|---|---|
| 죄책감 유발 금지 | "오늘의 구절이 준비되었습니다." | "3일째 필사를 안 하셨어요." |
| 연속기록 압박 금지 | "밤이 되기 전에, 한 구절." | "연속 기록이 끊어집니다!" |
| 신앙심을 평가하지 않음 | "요한 13,35 — 너희가 서로…" | "믿음이 식지 않으셨나요?" |
| 무인칭 (앱이 1인칭으로 말하지 않음) | "오늘의 구절이 준비되었습니다." | "제가 오늘 구절을 준비했어요!" |
| 내부 수치 비노출 | "이번 주 리듬이 이어지고 있습니다." | "이번 주 4/7 달성! 3회 남았어요" |
| 과장·감탄 금지 | "오늘 필사를 마쳤습니다." | "🎉 대단해요! 최고예요!" |

**주 알림 문구 (확정안)**
- 제목: `오늘의 구절` (고정, 매일 동일)
- 본문: `{출처} — {구절 첫 12자}…`  예) `요한 13,35 — 너희가 서로 사랑하면…`
- 전례 시기 첫날에만 제목을 바꾼다: `대림 시기가 시작되었습니다` 등 (연 5회 이내)

**저녁 회수 알림 문구 (확정안)**
- 제목: `오늘의 구절` / 본문: `아직 오늘의 자리가 비어 있습니다.`
- **"비어 있습니다"까지가 상한이다.** 그 이상 나가면 죄책감 문구가 된다.

| 알림 상태 | 명세 |
|---|---|
| 권한 미결정 | 예약하지 않는다 (예약해도 안 뜬다) |
| **권한 거부** | 예약하지 않는다. S8 설정 행을 "꺼짐(기기 설정)"으로 표시 (§S8). **제품은 위젯으로 성립한다** |
| 오류 — 예약 실패 | 조용히 재시도. 3회 실패 시 S8 설정 화면 진입 시에만 `알림 예약에 실패했습니다. (notif.schedule_failed)` 표기. 홈에서 사용자를 방해하지 않는다 |
| 오늘 이미 완료 | 저녁 알림은 발송하지 않는다 (예약 취소). **주 알림은 유지** — 아침에는 아직 안 했으므로 |
| 시각 변경 | 기존 예약 전부 취소 후 재예약 (부분 갱신 금지 — 중복 알림 사고의 단골 원인) |

### 6-3. 콘텐츠 주입 구조 — **성경 본문을 앱이 소유하지 않는다**

```
 [콘텐츠 저장소]            [CDN]                 [앱]
 pack-2026-08.json  ──►  manifest.json  ──►  ContentProvider (인터페이스)
 (본문 포함)              licenseState        ├─ RemoteProvider  (출시본)
 * 제품 git 저장소         packUrl[]           ├─ FixtureProvider (개발/테스트)
   바깥에서 관리           minAppVersion       └─ EmptyProvider   (회수 상태)
                                                      │
                                              기기 캐시 (최근 30일 + 다음 7일)
```

**규칙 (어기면 저작권 협의 자체가 위태로워진다)**

| # | 규칙 | 이유 |
|---|---|---|
| R1 | **성경 본문은 제품 git 저장소에 커밋하지 않는다.** 앱 번들에도 넣지 않는다 | 저장소·번들에 들어가는 순간 "앱이 성경을 배포"하는 형태가 된다. 리버스 엔지니어링으로 전권 추출도 가능해진다 |
| R2 | 앱은 `ContentProvider` 인터페이스로만 본문을 얻는다 | **저작권 승인 없이도 개발·QA가 끝까지 진행된다**(C2). `FixtureProvider`는 저작권 만료 문헌·자체 작성 문장으로 채운다 |
| R3 | 팩에는 `licenseId` / `sourceLabel`이 반드시 있고, **본문이 보이는 모든 표면에 출처가 함께 보인다** | 승인 조건이 대개 출처 표기다 |
| R4 | 앱은 실행 시 `manifest.json`의 `licenseState`를 확인한다 (`active` / `revoked`) | §6-5 |
| R5 | 사용자의 필사 결과는 **기기 밖으로 나가지 않는다.** 서버 업로드·백업 없음 | 2차 배포가 없으므로 사적 이용 범위에 머문다 |
| R6 | 팩 형식은 **날짜당 1구절**이 상한이다. 장 단위·권 단위 팩을 만들지 않는다 | 형식 자체가 총량을 제한하는 장치다 |

### 6-4. 인용 총량 가드레일

C1의 "30% 초과 시 별도 승인"을 **협상이 아니라 구조로** 지킨다.

- 하루 1구절 × 365일 ≈ 성경 전체 대비 0.1% 미만. **V1 형식은 구조적으로 30%에서
  아주 멀다** — 이것이 승인 협의에서 우리가 내밀 수 있는 가장 강한 카드다.
- 발행 파이프라인이 팩을 만들 때 **누적 인용 절 수 / 문자 수를 집계해 기록**한다
  (BE 담당). 이 수치는 CBCK 제출 문서에 그대로 쓴다.
- 위젯·알림의 발췌 상한(§5-1, §5-2)도 같은 이유다.
- **이 수치는 사용자 UI에 절대 노출하지 않는다** (PD 하네스: 내부 수치 비노출).

### 6-5. 회수(킬 스위치)

승인이 늦어지거나 조건이 바뀌면 **앱 재제출 없이** 본문만 내린다.

```
manifest.licenseState = "revoked"
   → 앱: 캐시된 focusText 삭제, EmptyProvider로 전환
   → S1: "오늘 본문을 표시할 수 없습니다. (content.unavailable)" + 출처만
   → 위젯: 전례일 + 출처만
   → 기존 사용자 기록(Transcription.bodyText)은 삭제하지 않는다 — 사용자 저작물이다
```

이 스위치가 **있다는 사실 자체가** C1 협의에서 우리의 위험을 낮춘다. PRD에 명시하는
이유다. (실제 발동은 비가역에 준하는 행동 → PO 승인 후 실행, TEAM.md §5)

## 7. 엣지케이스

### A. 날짜 경계 — **하루는 04:00에 바뀐다**

| 항목 | 결정 |
|---|---|
| **완료 귀속 경계** | 로컬 시각 **04:00**. 즉 8/14 01:30에 마친 필사는 **8월 13일**로 귀속 |
| **전례일 표시** | **실제 달력 날짜 기준** (교회 전례일은 자정에 바뀐다). 즉 01:30에는 화면에 8/14의 전례일이 뜨지만, 완료는 8/13에 찍힌다 |
| 이 불일치를 사용자에게 어떻게? | 00:00~04:00 사이에만 S1 상단에 한 줄: `아직 8월 13일의 필사로 기록됩니다.` |
| 왜 04:00인가 | 취침 전 사용 맥락(§2-2 B)에서 자정을 넘기는 사용자가 "하루를 놓쳤다"고 느끼는 것을 막는다. 03:00은 짧고 06:00은 아침 사용자와 겹친다 |

> ⚠️ 04:00과 "전례일은 실제 날짜"의 조합은 **구현이 헷갈리는 지점**이다.
> `todayForRecord()`와 `todayForLiturgy()`를 **함수 두 개로 분리**하고, 화면·위젯·
> 알림 어디서도 `new Date()`를 직접 쓰지 않는다. (팀 규칙 8: 단일 진실 공급원)

### B. 같은 날 중복 완료

- 하루에 여러 번 필사할 수 있다(S1의 [한 번 더 쓰기]). 그러나 **주간 도트는 하루 1개**.
- 딥링크가 완료된 날의 `write`로 들어오면 라우터가 S7로 대체한다 (§4-1).

### C. 연속기록 끊김 — **끊김을 벌하지 않는다**

| 항목 | 결정 |
|---|---|
| streak(연속) 카운터 | **UI에 노출하지 않는다.** 내부에도 두지 않는다 (없는 값은 새어 나오지 않는다) |
| 대신 | **주간 리듬** — 이번 주 O/목표. 주가 바뀌면 리셋된다. **끊김이라는 개념 자체가 없다** |
| 지난 날 채우기 | **최근 7일 이내** 미완료일을 소급 완료 가능. `isBackfilled=true`로 표시하되 **UI에서 차별하지 않는다**(도트 모양 동일). 기록 상세에서만 "8월 10일의 구절" 날짜로 구분됨 |
| 미래 날짜 | 불가. 팩은 있어도 쓰기 진입 차단 |
| 8일 이상 지난 날 | 채울 수 없다. 조용히 목록에 안 나온다 ("놓쳤습니다" 문구 없음) |
| 장기 이탈 후 복귀 | 재촉·요약·"OO일 만이네요" 금지. **그냥 오늘 화면이 뜬다** |

### D. 타임존 / 해외

| 상황 | 처리 |
|---|---|
| 사용자가 해외로 이동 | 전례일·팩은 **기기 로컬 날짜** 기준. 한국 고유 축일(103위 순교 성인 등)이 포함된 한국 전례력 데이터를 그대로 쓴다 |
| 시차로 같은 날짜가 두 번 오거나 하루가 사라짐 | 귀속일은 `date` 문자열(YYYY-MM-DD) 하나로만 판정한다. **UTC 타임스탬프로 하루를 계산하지 않는다** (표준시 전환·서머타임 사고의 원인) |
| 기기 시각을 수동으로 되돌림 | 이미 완료된 날짜를 다시 완료할 수는 있으나 도트는 1개다(§B). 부정 방지 로직은 넣지 않는다 — 속일 대상이 없는 제품이다 |

### E. 기기 변경

| 상황 | 처리 |
|---|---|
| iCloud 백업으로 복원 | 앱 샌드박스가 통째로 복원되므로 기록이 따라온다. **DB와 손글씨 파일 모두 백업 대상 디렉터리에 둔다** (`Documents`, `isExcludedFromBackup=false`) |
| 백업 없이 새 기기 | **기록은 사라진다.** 이 사실을 온보딩 3스텝과 S8 [내보내기] 옆에 명시한다. 숨기면 나중에 리뷰로 돌아온다 |
| 수동 내보내기 | S8 [내보내기(전체)] → 날짜별 텍스트 묶음(.txt/.md) + 손글씨 이미지 zip. **가져오기(import)는 V1에 없다**(X 목록에 추가 검토 — 내보내기만 있고 가져오기가 없으면 반쪽이라는 지적 가능. §10-E) |

### F. 오프라인 필사 후 동기화

- **동기화라는 개념이 한 방향뿐이다**: 서버 → 앱(콘텐츠 팩). 앱 → 서버는 **없다**.
- 오프라인 시나리오:
  1. 온라인일 때 **다음 7일치 팩을 미리 받아둔다** (앱 포그라운드 진입 시 확인).
  2. 오프라인이면 캐시로 필사·성찰·기록 모두 정상 동작.
  3. 온라인 복귀 시 팩 갱신만 일어난다. **사용자 기록은 아무것도 올라가지 않는다.**
- **팩 리비전이 바뀐 뒤 오프라인 기록이 있는 경우**: `Transcription.packRevision`이
  다르면 기록 상세에서 **내가 쓴 당시의 출처**를 보여준다(현재 팩으로 덮어쓰지 않는다).

## 9. 용어집 · 화자 규칙 · UX 라이팅 원칙

### 9-1. 화자 규칙 — **이 앱에는 캐릭터가 없다**

> 이것이 이 제품의 첫 번째 라이팅 결정이다. 종교 제품에서 1인칭 캐릭터가 신앙을
> 대변하면 교리적 발화 리스크를 앱이 떠안는다. 마스코트도, "저는~"도 없다.

화자는 **두 개뿐이고 절대 섞이지 않는다.**

| 화자 | 정체 | 문체 | 예 | 금지 |
|---|---|---|---|---|
| **A. 시스템 UI** | 무인칭. 앱은 자기를 지칭하지 않는다 | 평서형 `-ㅂ니다`체. 짧고 사실적 | "오늘 필사를 마쳤습니다." "알림이 꺼져 있습니다." | 1인칭("제가"), 감탄("대단해요!"), 반말, 이모지 |
| **B. 인용** | 성경 본문 · 교회 문헌 | **원문 그대로. 한 글자도 고치지 않는다** | "너희가 서로 사랑하면…" — 요한 13,35 | 요약, 현대어 풀이, 줄임(위젯 발췌는 `…`로 명시), 출처 누락 |

**섞임 방지 규칙**
- B(인용)는 **항상 시각적으로 분리된 컨테이너** 안에만 놓는다. 시스템 문장과
  같은 줄에 이어 쓰지 않는다.
- A는 **성경 문장을 흉내 내지 않는다.** "주님께서 함께하시길" 같은 축복문은
  시스템 UI가 할 말이 아니다 — 그건 사제·전례의 말이다.
- 알림 본문에서 A와 B가 만나는 유일한 지점은 `{출처} — {발췌}…` 형식이며,
  A 부분(제목 `오늘의 구절`)과 B 부분이 필드로 분리돼 있다.

### 9-2. 보상·기록 은유 — **'달란트'를 가져오지 않는다**

개신교 앱의 '달란트'는 ① 개신교 설교 전통의 어휘이고 ② **화폐 은유**다.
가톨릭 정서에서 신앙 실천에 화폐를 붙이면 면벌부·헌금 연상으로 번지고,
심사 관점에서도 "가상 화폐 → IAP 유도"로 읽힐 위험이 있다.

| 후보 은유 | 평가 | 채택 |
|---|---|---|
| **쪽(페이지)** — "8월 12쪽", "올해 200쪽" | 화폐가 아니라 **기록물의 두께**. 필사와 의미가 직결. 종교색이 없어 부담도 없음 | ✅ **채택** |
| 묵주알 | 가톨릭 고유성 최고. 그러나 묵주 기도(로사리오)는 **다른 신심 행위**라 혼동 유발 | ❌ |
| 등불 / 밀알 / 씨앗 | 성경 비유라 자연스러우나 **성장·수확 게임 은유**로 미끄러지기 쉽다 | ❌ |
| 봉헌 | 전례 용어를 앱 카운터에 쓰는 것은 무겁고, 헌금 연상 | ❌ |
| 포인트·코인·레벨·뱃지·랭킹 | 전부 금지 | ❌ |

**'쪽'의 사용 규칙**
- 표기: `12쪽` (조사 없이 명사 단독). "12쪽을 모았어요" 같은 수집 문구 금지.
- **교환·소비 개념을 만들지 않는다.** 쪽으로 무언가를 사거나 열 수 없다.
  쌓이기만 한다 — 그래서 IAP 유도로 읽힐 여지가 없다.
- 표시 위치: S6 기록 하단 한 곳뿐. 홈·알림·위젯에는 넣지 않는다.

### 9-3. 용어집 (단일 진실 공급원)

> 아래 표에 없는 말을 새로 쓰려면 이 표에 먼저 추가한다. 표면마다 다른 말을 쓰면
> 브랜드가 흐려진다 (PD 하네스 규칙표).

| 개념 | ✅ 쓰는 말 | ❌ 안 쓰는 말 | 비고 |
|---|---|---|---|
| 핵심 행위 | **필사하다 / 옮겨 쓰다** | 따라쓰기, 베끼기, 작성하다, 타이핑 | "쓰다"는 짧은 자리(버튼)에서 허용 |
| 완료 | **마치다** ("오늘 필사를 마쳤습니다") | 달성, 성공, 클리어, 완료했어요 | |
| 오늘의 대상 | **오늘의 구절** | 오늘의 말씀, 데일리 버스, 오늘의 큐티 | "말씀"은 개신교 어휘색이 강하고 범위가 넓다. **"구절"로 통일** |
| 성경 본문 총칭 | **성경** / 「성경」(2005) | 바이블, 성서 | 한국 천주교 공식 명칭은 「성경」 |
| 미사 독서 | 제1독서 / 제2독서 / 화답송 / **복음** | 본문, 오늘의 성경구절 | 전례 정식 명칭 |
| 성찰 입력 | **한 줄 / 그날의 한 줄** | 일기, 소감, 후기, 메모 | |
| 침묵 시간 | **머무는 시간** | 명상, 묵상 타이머, 힐링 타임 | "명상"은 타 종교·웰니스 어휘 |
| 렉시오 단계 | 독서 / 묵상 / 기도 / 관상 | (영어 병기는 설명 화면에서 1회만) | |
| 축적 | **쪽** | 달란트, 포인트, 코인, 스탬프 | §9-2 |
| 주간 진행 | **이번 주 리듬** | 연속 기록, 스트릭, 출석 | §7-C |
| 소급 완료 | **지난 날 채우기** | 결석 보충, 놓친 날, 만회하기 | "놓쳤다"는 어휘 자체를 안 쓴다 |
| 전례 기간 | **시기** (대림 시기, 사순 시기) | 절기, 시즌 | "절기"는 개신교/농경 어휘 |
| 저장물 | **기록** | 아카이브, 히스토리, 보관함 | |
| 사용자 호칭 | **호칭하지 않는다** (2인칭 생략) | 형제님, 자매님, 성도님, 회원님 | 신자 여부·성별을 앱이 단정하지 않는다 |

**조사(助詞) 규칙**
- 출처·축일명 뒤에 **조사를 자동으로 붙이지 않는다.** 받침 판정이 필요한
  템플릿(`{출처}을/를`)을 만들지 않는다. 문장을 조사 없이 끝내도록 설계한다.
  예) ✅ `요한 13,35 — 너희가 서로…` / ❌ `요한 13,35을 필사할 시간입니다`
- 사용자가 입력한 텍스트를 시스템 문장에 끼워 넣지 않는다(같은 이유).

### 9-4. 라이팅 원칙 5조

1. **평가하지 않는다.** 신앙심·성실함·연속성을 칭찬하거나 아쉬워하지 않는다.
2. **재촉하지 않는다.** 미완료는 "비어 있는 자리"까지가 표현의 상한이다.
3. **감탄하지 않는다.** 느낌표와 축하 이모지를 UI에서 쓰지 않는다.
4. **설명하지 않는다.** 오류 문구에 내부 사정을 쓰지 않는다. 대신 **오류 코드를
   붙인다** (팀 규칙 6). 사용자에겐 "무엇을 할 수 있는가"만 준다.
5. **내부 수치를 노출하지 않는다.** 완료 판정 임계값, 캐시 일수, 발췌 글자 수,
   인용 총량 — 전부 문구에 넣지 않는다 (PD 하네스 규칙표).

### 9-5. 시각 토큰 초안 (디자인 시스템 문서로 분리 예정)

**전례 시기 색이 앱의 액센트를 지배한다** — 이것이 가톨릭 고유성의 시각적 핵심이다.

|---|---|---|
| 대림 / 사순 | 자주 | `violet.700` |
| 성탄 / 부활 | 백색(금) | `gold.600` (흰 배경에 대비 확보) |

| 성령강림·순교자 축일 | 홍색 | `red.700` |
| 기쁨의 주일 (대림 3주 · 사순 4주) | 장미 | `rose.500` |

- **로딩 스피너를 전체 화면에 쓰지 않는다** — 스켈레톤 우선 (§4 상태 명세).

권고 이유 3가지:
1. **한글 손글씨의 물리적 한계.** 한글은 획이 많고 모아쓰기라 손가락 입력 시
   구절 하나에 5~8분이 든다 — §2-2 세션 상한을 넘긴다. 실패 시 되돌릴 수 없다.
2. **V1의 차별화는 입력 방식이 아니라 §P1·P2(마찰 제거 + 상기 표면)에 있다.**
   위젯·알림이 우리의 무기다. 입력 방식에 3주를 더 쓰면 무기를 늦게 낸다.
3. A안으로 먼저 내면 **B안이 정말 필요한지 데이터로 알 수 있다** (§8-3 필사
   완료율 70% 미만이면 신호).

**단, PO가 "아날로그 감각이 이 제품의 존재 이유"라고 판단하면 B안이 옳다.**
그 경우 세션 시간 상한을 9분으로 올리고, 구절 길이를 짧은 것 위주로 큐레이션하고
(§6-2 팩 편집 규칙 추가), 스타일러스 사용자를 별도 세그먼트로 인정해야 한다.
**C안은 권고하지 않는다** — V1에서 두 벌을 만들면 어느 쪽도 완성도가 안 난다.

**❓ APP 팀 선확인 요청** (하네스 에스컬레이션: "설계 후 불가 판정이 제일 비싸다"):
Expo 환경에서 ① `react-native-skia` 기반 필기 캔버스의 지연·되돌리기 구현 난이도,
② WidgetKit 위젯 + App Group 공유가 Expo 개발 빌드에서 문제없는지 —
**이 두 가지는 PO 결정 전에 APP의 답이 필요하다.**

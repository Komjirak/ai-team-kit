## 1. 문제 정의 · 피벗 이유

### 1-1. 풀려는 문제 — 무게중심은 "여행 후"에 있다

친구들의 여행에는 앱이 많다. 트리플·Wanderlog가 **계획**을 잘 돕고, 지도 앱이 **길**을
안내한다. 그런데 정작 **여행이 끝난 뒤**의 두 가지가 매번 빈다 —

- 🎯 **다녀온 뒤 기록이 사라진다.** 사진은 각자 폰에, 후기는 아무 데도 없다. 함께 만든
  추억이 **공동의 기록으로 남지 않는다.** ← **이 제품이 푸는 첫 번째 문제**
- 🎯 **정산이 여행 후로 밀리고, 감정이 상한다.** 누가 뭘 냈는지 기억이 흐려진 뒤 누군가
  엑셀을 켜고, 1/N 계산과 독촉이 관계를 긁는다. ← **두 번째 문제**

이 두 가지가 **주인공**이다. 계획 단계의 불편(일정이 흩어지고, 갈 곳이 안 합쳐짐)도
있지만 그건 이미 잘하는 앱이 많다 — 우리는 그걸 **가볍게 받쳐주는 조연**으로만 둔다.

> **한 문장:** *"풀 여행 플래너를 또 만들지 않는다. 친구와 함께 **여행 기억을 남기고,
> 돈을 가볍게 정산하는** 도구를 만든다."* (PO/BD 확정, §포지셔닝)

### 1-2. 왜 Datel.log에서 피벗하는가

Datel.log는 **커플 2인**이 "함께 간 곳"을 **기록**하는 앱이다 — 즉 이미 **회고·기억장**
제품이다. 핵심 협업 구조(**초대코드로 묶여 같은 데이터를 실시간으로 본다**)와 **스크랩북
회고(Memory·폴라로이드)** 는 이미 검증됐다. 인원 제약(1:1)을 N인으로 풀고, 여행 후
피로의 나머지 절반인 **정산(가계부)** 을 얹으면 **친구 여행 기억장 + 가벼운 정산**이 된다.
계획용 3모듈(일정·캘린더·장소)은 회고·정산을 **받치는 최소한**만 얹는다 — 풀 플래너로
키우지 않는다(§4 포지셔닝).

| 승계 자산 | Datel.log에서 | (가제)에서 |
|---|---|---|
| **디자인 컨셉** | "Dakku" 스크랩북(washi tape·pin·polaroid·grid paper) | 그대로 승계 — 여행 스크랩북 톤과 잘 맞는다 (§10 PD가 확정) |
| **초대 페어링** | 초대코드 1회 결합 · Couple(memberIds ≤ 2) | **초대링크**로 N인 합류 · Trip(memberIds 무제한) |
| **장소 도메인** | `Place`(Kakao 검색·핀·카테고리·wishlist/visited) | 그대로 확장 — `coupleId` → `tripId`, 일정에 연결 |
| **회고 도메인** | `Memory`(사진·후기·폴라로이드 그리드) | 그대로 확장 — 여행 회고로 |
| **Kakao Maps** | SDK 로더·RouteMap 동선·장소 검색 | 승계 (해외 대응은 §12 오픈이슈 C) |
| **Firebase** | Auth(Google)·Firestore(실시간 구독)·Storage | 승계 + FCM 웹푸시 추가 |
| **백엔드 추상화** | `Backend` 인터페이스 하나로 데모↔운영 전환 | 승계 — 신규 엔티티(Trip·Expense 등)로 인터페이스 확장 |
| **실시간 구독** | `watchPlaces`/`watchMemories` 패턴 | 승계 — `watchSchedule`/`watchExpenses` 추가 |

> **피벗의 본질:** 신규 개발이 아니라 **"협업 단위 1:1 → N인 확장 + 여행용 3모듈 추가"** 다.
> 이 프레이밍을 잊고 전면 재작성으로 접근하면 크기가 V1을 넘는다(§4 참조).

## 2. 타깃 · 사용 맥락

### 2-1. 타깃

- **1차:** 국내·근거리 자유여행을 **2~6인 친구 그룹**으로 준비하는 20~30대. 카톡방 +
  메모장 + 개인 저장으로 흩어져 준비하다 정산에서 피로를 겪는 사람들.
- **협업 단위:** 여행 1건 = 멤버 모임 1개. (같은 친구들이 여러 여행을 재사용하는
  "그룹 저장"은 v1.0.0 범위 밖 — §12 오픈이슈 D)

### 2-2. 사용 맥락 — 여행의 세 국면 (제품이 따라가는 축)

| 국면 | 언제 | 주로 쓰는 모듈 | 사용자가 겪는 것 |
|---|---|---|---|
| **여행 전 (계획)** | 출발 며칠~몇 주 전 | 그룹/초대 · 일정 · 장소 | 링크로 친구를 부르고, 일자별로 갈 곳을 함께 짠다 |
| **여행 중 (실시간)** | 현지에서 | 일정 · 장소 · 가계부 | 오늘 일정을 확인하고, 쓴 돈을 그 자리에서 입력한다 |
| **여행 후 (정산·회고)** | 돌아온 뒤 | 가계부/정산 · 회고 | 정산으로 돈을 정리하고, 사진·후기로 되돌아본다 |

> **설계 원칙:** 여행 중은 **네트워크가 불안정하고 손이 바쁘다.** 비용 입력·일정 확인은
> 최소 탭으로 끝나야 한다. (오프라인 완전 대응은 Won't — §4, 다음에 키울 목록)

## 4. v1.0.0 범위 — MoSCoW

> **범위는 "넣을 것"이 아니라 "뺄 것"으로 지킨다.** Won't(§4-4)가 이 PRD의 계약이다.
> 크기가 V1을 넘으면 자동 연장하지 않고 Should를 Won't로 내린다(다시 자르기).

### 4-1. Must — v1.0.0이 동작한다고 말하려면 반드시 있어야 하는 것

| 모듈 | Must 항목 |
|---|---|
| ① 여행/그룹 | Google 로그인(승계) · 여행 생성(제목·목적지·기간) · **초대링크 발급·합류** · 멤버 목록 · 여행 나가기 |
| ① 권한 | **owner / member 2단계**(§5-2). owner=여행 삭제·멤버 제거·정산 확정, member=일정·장소·비용·회고 편집 |
| ② 일정 | **인앱 캘린더가 기본(단일 기준)** · 일자별(Day) 일정 항목 CRUD — 날짜·시간·제목·메모·순서. 리스트 뷰(일자 그룹핑) |
| ③ 장소 | Kakao 검색·핀·장소 카드(승계) · 장소를 **일정 항목에 연결** · 여행 지도(핀 모음) |
| ④ 가계부 | 비용 입력(제목·금액·결제자·참여자) · **1/N 균등 분담 정산 계산**(누가 누구에게 얼마) · 정산 요약 · **정산 완료 체크("정산됨" 표시)** |
| ⑤ 회고 | 여행 후 사진(Storage 승계)·후기 · 폴라로이드 그리드(승계) |
| 알림 | **FCM 웹푸시** — 초대 합류 · 일정 변경 · 정산 요청 3종 · 옵트인(§6) |
| 공통 | 실시간 구독(승계) · 데모 모드(키 없이 전체 흐름, 승계) · 로딩/빈/오류 상태 |

### 4-2. Should — v1.0.0에 있으면 좋지만, 크기가 넘치면 가장 먼저 Won't로 내린다

- **Google Calendar 동기화(옵셔널 미러링)** — **인앱이 source of truth**, 로그인한
  Google 계정이 연동돼 있으면 여행 일정을 구글캘린더로 미러링. 앱 자체 Google OAuth
  스코프(`calendar.events`)로 구현(별도 커넥터 아님). **미연동·스코프 미허용 시 인앱만
  동작**(§6-3). ⟵ 오픈이슈 B 확정(PO, 2026-08-31)
- **캘린더 그리드 뷰**(월/주) — Must는 리스트 뷰, 그리드는 Should
- **정산 확정 워크플로우** — owner가 "정산 확정" → 스냅샷 저장 + 정산요청 푸시
- **분담 방식 확장** — 개별 지정(특정 인원만) · 비율 분담 (Must는 1/N 균등만)
- **일정 동선 지도** — 하루 일정을 순서대로 이은 RouteMap(Course 승계)

### 4-3. Could — 여유가 있을 때만. 없어도 v1.0.0이라 부를 수 있다

- 비용 카테고리(식비·교통·숙박)별 통계
- 회고 하이라이트 자동 구성(사진 많은 날 강조)
- 여행 D-day 카운트다운 · 여행 후 요약 카드(총 지출·방문 수)

### 4-4. Won't — v1.0.0에서 **뺀다** (= "다음에 키울 목록", 버리는 게 아님)

| 뺀 것 | 왜 지금 빼는가 | 언제 키우나 |
|---|---|---|
| **실시간 위치 공유** | 배터리·프라이버시·권한 복잡도가 크다. 여행 중 핵심 아님 | v1.2+ |
| **항공·숙소 예약 연동** | 외부 API 계약·수수료 모델 필요. 사업 결정(BD) 선행 | v2 |
| **다국어(i18n)** | 1차 타깃 국내. 문자열 외부화 구조만 남긴다 | 해외 확장 시 |
| **실제 송금 · PG 연동**(토스/뱅킹) | 금융 연동은 규제·심사·계약. 정산은 **계산·요약·완료 체크("정산됨" 표시)까지만** v1 포함, 실제 돈 이동은 제외 | v2 (오픈이슈 A 확정) |
| **다중 통화·환율** | 국내 여행 KRW 고정. 해외 대응과 함께 | 해외 확장 시(오픈이슈 F) |
| **그룹 재사용**(친구 모임 저장) | 여행 단위로 단순화. 매번 초대링크로 충분 | v1.1 (오픈이슈 D) |
| **viewer(읽기전용) 권한** | 2단계로 시작. 3단계는 근거 쌓인 뒤 | v1.1 (오픈이슈 E) |
| **다크모드 · PWA 오프라인** | 토큰·SW 구조만 남긴다(푸시용 SW는 별개) | v1.x |
| **네이티브 앱** | 반응형 웹으로 검증 먼저 | 검증 후 |
| **소셜 피드·탐색·여행 추천/AI 일정** | 협업 도구가 먼저. 콘텐츠 제품은 다른 사업 | v2+ |

## 5. 데이터 모델 초안

> Datel.log의 `src/data/types.ts`를 기준으로 확장한다. **핵심 변경: `coupleId` → `tripId`,
> `Couple`(≤2) → `Trip`(N인) + `Membership`(권한 분리).** 백엔드 추상화(`Backend`
> 인터페이스)와 데모/Firebase 두 구현 패턴은 승계하고 신규 엔티티만 얹는다.

### 5-1. 엔티티

```
AppUser        승계 확장. coupleId 제거 → 멤버십으로 소속 파악. fcmTokens[] 추가(웹푸시)
Trip           신규(Couple 승계 확장). 여행 = 협업 단위
Membership     신규. 누가 어느 여행에 어떤 권한(role)으로 속하는가
ScheduleItem   신규. 일자별 일정 항목 (Day는 startDate~endDate에서 파생)
Place          승계. coupleId → tripId, scheduleItemId? 연결
Expense        신규. 비용 항목 (결제자·참여자·분담)
Settlement     신규(대부분 파생). 정산 결과. Must=계산만, 확정 시 스냅샷 저장(Should)
Memory         승계. coupleId → tripId
AppNotification 승계 확장. type에 여행용 3종 추가 + FCM 연동
```

```ts

export interface Trip {
  id: string
  inviteToken: string        // 초대링크의 토큰 (Datel의 inviteCode 승계·확장, §6-1)
  title: string              // "제주 3박4일"
  destination?: string       // 목적지 라벨
  startDate?: string         // ISO yyyy-mm-dd
  endDate?: string           // ISO yyyy-mm-dd — Day는 start~end에서 파생
  coverPhoto?: string        // 대표 사진 URL (Couple.coverPhoto 승계)
  ownerId: string            // 생성자 = owner
  memberIds: string[]        // N인 (Couple.memberIds ≤2 제약 해제)
  createdAt: number
}

// 신규 — 권한을 Trip에서 분리 (오픈이슈 E에서 단계 수 확정)
export interface Membership {
  tripId: string
  userId: string
  role: 'owner' | 'member'   // v1.0.0 2단계. viewer는 Won't(§4-4)
  nickname: string           // 이 여행에서의 표시 이름
  joinedAt: number
}

// 신규 — 일자별 일정 (인앱이 source of truth)
export interface ScheduleItem {
  id: string
  tripId: string
  date: string               // ISO yyyy-mm-dd (어느 Day인지)
  order: number              // 같은 날 안에서의 순서
  time?: string              // "14:30" (선택)
  title: string
  placeId?: string           // 장소 연결 (③ 모듈)
  memo?: string
  googleEventId?: string     // 구글캘린더 미러링 시 대응 이벤트 id (Should §4-2·§6-3)
  createdBy: string
  createdAt: number
}

// 신규 — 비용
export interface Expense {
  id: string
  tripId: string
  title: string
  amount: number             // KRW (v1 통화 고정, 오픈이슈 F)
  paidBy: string             // 결제자 userId
  participantIds: string[]   // 분담 대상
  splitType: 'equal'         // v1.0.0 1/N 균등만. 'individual'|'ratio'는 Should(§4-2)
  category?: string          // Could(§4-3)
  spentAt: string            // ISO yyyy-mm-dd
  createdBy: string
  createdAt: number
}

// 신규 — 정산. Must=파생 계산 + 완료 체크. 확정 스냅샷은 Should
export interface Settlement {
  tripId: string
  transfers: Transfer[]      // 누가→누구에게 (1/N 균등 결과)
  perMember: { userId: string; paid: number; owed: number; net: number }[]
  confirmedAt?: number       // owner 확정 시각 (Should §4-2)
  confirmedBy?: string
}

// 정산 항목별 "정산 완료 체크" — Must(§4-1, 오픈이슈 A 확정)
export interface Transfer {
  from: string               // 갚을 사람
  to: string                 // 받을 사람
  amount: number             // KRW
  settled: boolean           // "정산됨" 표시 (실제 송금/PG는 Won't §4-4)
  settledAt?: number
}
```

- **Place / Memory 승계 변경:** 인터페이스 유지, `coupleId` → `tripId`. Place에
  `scheduleItemId?` 추가(일정 연결). `status`(wishlist/visited)는 "가고싶은 곳/다녀온 곳"
  으로 여행 맥락에 그대로 맞는다.
- **AppNotification 승계 변경:** `coupleId` → `tripId`, `type`에
  `member_joined | schedule_changed | expense_added | settlement_requested` 추가.
- **AppUser 승계 변경:** `coupleId` 제거(멤버십이 대체), `fcmTokens?: string[]` 추가,
  `googleCalendar?: { linked: boolean; scopeGranted: boolean }` 추가 — 구글캘린더 미러링
  연동 상태(§6-3). 앱 자체 Google OAuth로 얻은 `calendar.events` 스코프 허용 여부.

### 5-2. 권한 (누가 무엇을)

| 행동 | owner | member |
|---|---|---|
| 일정·장소·비용·회고 **추가/수정/삭제** | ✅ | ✅ (본인 생성분 + 공동편집) |
| 멤버 **초대링크 발급** | ✅ | ✅ (오픈이슈 G에서 확정) |
| 멤버 **제거** · 여행 **삭제** | ✅ | ❌ |
| **정산 확정**(스냅샷) | ✅ | ❌ |
| 여행 **나가기** | (owner 이양 필요) | ✅ |

> **결정 대기:** 3단계(viewer 추가) 필요 여부 = 오픈이슈 E. member의 삭제 권한 범위
> (본인 생성분만 vs 전체 공동편집)는 PD 상태 명세와 함께 확정.

## 6. 초대링크 · 푸시 알림 · 캘린더 동기화

### 6-1. 초대링크 (Datel 초대코드 승계·확장)

- Datel은 6자리 **코드**를 사람이 입력해 1회 결합했다. Travel은 **링크**(`/join/:inviteToken`)로
  확장 — 카톡·SNS로 공유, 탭 한 번으로 합류. 코드 입력 흐름도 폴백으로 유지 가능.
- 링크 클릭 → 미로그인 시 Google 로그인 → 여행 미리보기(제목·멤버 수) → "합류" → Membership 생성.
- **미결:** 링크 만료·재발급·승인제 여부 = 오픈이슈 G(보안 트레이드오프).

### 6-2. 푸시 알림 (FCM 웹푸시)

- **전제:** Firebase Cloud Messaging **웹푸시**. Service Worker 1개 필요(오프라인 캐싱과
  무관한 푸시 전용 SW — 그래서 PWA 오프라인이 Won't여도 푸시는 가능).
- **옵트인:** 브라우저 알림 권한을 **명시적 시점에** 요청(합류 직후·설정에서). 거부해도
  인앱 알림(Datel `NotificationBell` 승계)은 동작 — 푸시는 부가.
- **v1.0.0 알림 3종:**

| 알림 | 트리거 | 받는 사람 |
|---|---|---|
| 멤버 합류 | 초대링크로 새 멤버 합류 | 기존 멤버 전원 |
| 일정 변경 | ScheduleItem 추가/수정/삭제 | 본인 제외 멤버 (묶음/디바운스 권장) |
| 정산 요청 | owner 정산 확정(Should) 또는 정산 요청 액션 | 갚을 사람(net<0) |

> **주의(팀 규칙 6):** 알림 실패·권한 거부는 **원인 코드와 함께** 노출한다
> (`push.denied` / `fcm.token_failed`). "알림이 안 와요"를 진단 가능하게.

### 6-3. Google Calendar 동기화 (Should · 옵셔널 미러링) — 오픈이슈 B 확정(PO)

- **인앱 캘린더가 source of truth.** 구글캘린더는 **한 방향 미러링**(인앱 → 구글)이
  기본이다. 인앱 일정을 정본으로 두고, 연동 시 구글캘린더에 사본을 만든다.
- **구현 방식:** **앱 자체 Google OAuth 스코프(`calendar.events`)** — Datel이 이미 쓰는
  Google 로그인(Firebase Auth)에 캘린더 스코프를 **증분 요청**한다. **별도 커넥터가 아니다.**
- **동작 조건:** 로그인한 Google 계정이 **연동돼 있고 스코프를 허용한 경우에만** 미러링.
  **미연동·스코프 거부 시 인앱만 동작**(기능 저하 없음 — 미러링은 부가).
- **데이터:** ScheduleItem 생성/수정/삭제 시 대응 구글 이벤트를 생성/수정/삭제하고
  `googleEventId`로 연결(§5). 삭제 시 미러 이벤트도 정리.
- **범위 경계:** v1.0.0은 **인앱 → 구글 단방향.** 구글에서 편집한 것을 인앱으로 되받는
  **양방향 동기화는 Won't**(충돌 해소 복잡도) — 다음에 키울 목록.
- **오류 노출(팀 규칙 6):** 스코프 거부·동기화 실패는 원인 코드로(`gcal.scope_denied` /
  `gcal.sync_failed`). 미러링 실패가 인앱 일정 저장을 막지 않는다(인앱 우선).

## 8. 성공 기준 (숫자 — 제안치, PO 확정 대상)

### 8-1. v1.0.0 "동작한다"의 정의 (QA 게이트 · 릴리즈 판정 기준)

> **4인 그룹**이 여행 1건을 아래 흐름으로 **오류 없이 완주**하면 v1.0.0이다.
> 데모 모드 + 실제 Firebase 두 경로 모두에서 통과해야 한다.

```
여행 생성 → 초대링크로 3인 합류(총 4인) → 3일 일정에 항목 12개 이상 →
장소 10곳 검색·핀·일정 연결 → 비용 15건 입력(균등 분담) →
정산 계산 정확(수기 검산과 일치) → 회고 사진·후기 → 알림 3종 수신
```

### 8-2. 제품 지표 (출시 후, 제안치)

| 지표 | 제안 목표 | 왜 이 숫자 |
|---|---|---|
| **초대 합류율** | 초대링크 수신자의 **60%+** 합류 | N인 협업 제품의 생명. 절반 이상 합류해야 그룹이 성립 |
| **정산 완주율** | 여행 생성 그룹의 **50%+** 가 정산까지 도달 | 가계부가 v1 차별 가치 — 정산이 실제로 쓰여야 성공 |
| **여행당 활성 멤버** | 평균 **3인+** 가 일정·비용에 1건 이상 기여 | "한 명이 다 하는" 협업 실패를 거른다 |
| **여행 후 회고 작성률** | 완료 여행의 **40%+** 에 회고 1건+ | 재방문·다음 여행 재생성의 선행 지표 |

> **주의(팀 규칙):** 위 수치는 사용자 표본 전 **제안치**다. BD의 BUSINESS_CASE(§12 D0)가
> 나오면 시장 근거로 교정한다. 내부 목표 수치를 사용자 대면 문구에 넣지 않는다.

## 9. 엣지케이스 · 상태 (PD 상태 명세의 입력)

- **빈 상태:** 멤버 1인(합류 전) · 일정 0건 · 비용 0건 · 회고 0건 각각의 빈 화면.
- **정산 엣지:** 참여자 1인 · 결제자=유일 참여자(정산 불필요) · 금액 0 · 소수점 반올림
  잔여(1원 오차 배분 규칙) · 나간 멤버가 낀 비용 · 참여자 없는 비용(입력 검증).
- **일정 엣지:** 기간 미설정 여행의 일정 · 기간 밖 날짜 항목 · 같은 시간 중복 항목.
- **캘린더 동기화 엣지:** 스코프 미허용(인앱만) · 미러링 실패 시 인앱 저장은 유지 ·
  연동 해제 후 남은 구글 이벤트 처리 · 여러 멤버가 각자 자기 구글캘린더로 미러링(§6-3).
- **정산 완료 엣지:** 일부만 "정산됨" 표시된 상태 · 정산 후 비용 추가로 잔액 변동 ·
  "정산됨" 되돌리기.
- **권한 엣지:** owner가 나갈 때 이양 · 마지막 멤버가 나갈 때 여행 처리 · member의 타인 생성분 편집 시도.
- **초대 엣지:** 만료/무효 토큰 · 이미 합류한 멤버의 재클릭 · 삭제된 여행의 링크.
- **네트워크:** 여행 중 오프라인 입력(재시도 큐 여부는 Won't 경계 확인) · 지도 로드 실패(`map.load_failed` 승계).
- **푸시:** 권한 거부 · 토큰 만료 · 다중 기기.

> 각 상태의 **화면·문구·복구 동선**은 **§10에서 PD가 확정**한다. 여기서는 목록만 남긴다.
